# Native P1.2 — MCP and First-Party Tools Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A native-provider session exposes and can call (a) user-configured MCP servers and (b) the in-process first-party tool servers, with the same permission, status and dynamic-server surfaces the claude provider already has.

**Architecture:** One MCP client layer per native session. Every entry in the manager-resolved `CreateSessionOptions.mcpServers` map is connected through the `@modelcontextprotocol/sdk` `Client`; first-party entries arrive as `{ type: 'sdk', name, instance }` (the manager's existing `injectAll`) and are connected over an `InMemoryTransport` pair, so in-process tools and external servers share one discovery/call/status path and first-party tools keep the SDK's own Zod validation. Discovered tools become native `ToolDef`s named by one shared, API-safe `mcpToolFqn(server, tool)` builder (the same string the permission broker, the registry and the client's MCP-Apps mapping use). Connections start asynchronously after spawn (`pending` → `connected` / `failed` / `needs-auth`); a failed server never blocks the session.

**Tech Stack:** TypeScript ESM (`.js` suffixes), Node 20, `@modelcontextprotocol/sdk` 1.29 (already a direct dependency; the agent SDK peers on the same line), vitest, no new dependencies.

**Spec:** `docs/superpowers/specs/2026-11-09-native-session-persistence-design.md` (add a P1.2 section in Task 6).

## Global Constraints

- No behavior change for `server/providers/claude/**`; the transport extraction must keep `testMcpConnection` / `startMcpOAuth` / `finishMcpOAuth` equivalent.
- No new dependencies; Node 20 only; diagnostics through `createLogger`.
- Tool names exposed to the model are `mcpToolFqn(server, tool)` — `^[A-Za-z0-9_-]{1,64}$` is an Anthropic API requirement, so sanitization is mandatory. Built-in native tools keep their bare names (`Read`, `Write`, `Edit`, `Bash`, `Grep`) — the broker's `SAFE_AUTO_TOOLS` / `READONLY_TOOL_NAMES` already list those.
- Never `JSON.stringify` an MCP server entry: `type:'sdk'` entries contain a live server instance and throw on circular structures.
- The manager owns the merge (globals + inline + first-party injection) and the persisted `mcpServerNames`; the native provider must not re-merge globals or maintain that list.
- `setMcpServers` has **replace** semantics and returns `McpSetServersResult` (`{ added, removed, errors }`).
- A failing/slow MCP server must never fail the session create, block a turn indefinitely, or leak a child process: `status` becomes `failed`/`needs-auth` with an `error`, its tools are absent, and a timed-out connect is closed (which kills the stdio child).
- Status is never transformed server-side; it must never contain `env` or `headers` values (`args`/`command`/`url` are included, matching the CLI's own status).
- Tests: focused first; full gate `npm run typecheck && npm run test` before the final commit.

## Review Focus

1. **API-safe, consistent tool names** — model name, permission name, broker read-only exemption and the client's MCP-Apps mapping all come from `mcpToolFqn`; a hostile/long server or tool name can never 400 the request.
2. **Connection lifecycle** — destroy/delete closes every client and in-memory instance; a timed-out connect closes its transport (child killed); replace/toggle while a turn runs never mutates the in-flight tool list; no double-connect of a `type:'sdk'` instance.
3. **Freshness of the tool list** — the first turn after create waits for the connect barrier and then rebuilds; a replace/toggle/reconnect takes effect on the next turn, not mid-turn.
4. **Status parity** — `name/status/serverInfo/error/config/scope/source/tools` match what SettingsPanel and `useMcpApps` consume; first-party entries carry `source:'sdk'`; nothing secret leaks.
5. **Result + permission integrity** — MCP content maps to one capped text `tool_result` with `is_error` preserved; permission requests carry `mcpServer {name, source}` and the FQN.
6. **Test realism** — at least one real stdio transport (not just `type:'sdk'`) proves connect→list→call→close, including the child being killed; the e2e asserts the actual request `tools` array.

Each line gets a test in the owning task.

**Interfaces:**
- Produces:
  ```ts
  /** The one model-facing tool name for an MCP tool: `mcp__{server}__{tool}`,
   *  sanitized to the Anthropic API charset and ≤64 chars. */
  export function mcpToolFqn(server: string, tool: string): string
  ```
  Rules: `raw = \`mcp__${server}__${tool}\``; replace every `[^A-Za-z0-9_-]` with `_`; if the sanitized string differs from `raw` or exceeds 64 chars, truncate the sanitized base to 55 chars and append `_` + an 8-hex FNV-1a hash of `raw` (dependency-free — the client imports this module, so no `node:crypto`); result is always ≤64. Valid inputs are returned unchanged (`mcp__git-tools__git_status`).

  ```ts
    type: 'stdio' | 'sse' | 'http' | 'sdk'
    command?: string; args?: string[]; env?: Record<string, string>
    url?: string; headers?: Record<string, string>
    instance?: { connect(t: Transport): Promise<void>; close(): Promise<void> }
  }
  export interface NativeMcpToolInfo {
    server: string; name: string; fqn: string
    description: string
    inputSchema: Record<string, unknown>
    annotations?: Record<string, unknown>
    meta?: Record<string, unknown>
    rawName: string   // server-side tool name for callTool
  }
  export interface NativeMcpStatus {
    name: string
    status: 'connected' | 'failed' | 'needs-auth' | 'pending' | 'disabled'
    serverInfo?: { name: string; version: string }
    error?: string
    config?: { type: string; command?: string; args?: string[]; url?: string }
    scope: 'session'
    source?: 'sdk'
    tools?: Array<{ name: string; description?: string; annotations?: Record<string, unknown>; _meta?: Record<string, unknown> }>
  }
  export class NativeMcpConnections {
    constructor(opts?: {
      authFor?: (name: string) => OAuthClientProvider | undefined
      connectTimeoutMs?: number   // 10_000
      toolTimeoutMs?: number      // 120_000
    })
    /** Start connecting the map; returns immediately. Serialized with every
     *  later mutation through one queue. */
    load(servers: Record<string, unknown> | undefined): void
    /** Resolves when the mutation queue (including in-flight connects) drains. */
    whenReady(): Promise<void>
    statuses(): NativeMcpStatus[]
    tools(): NativeMcpToolInfo[]
    call(fqn: string, args: Record<string, unknown>, signal: AbortSignal): Promise<{ text: string; isError?: boolean }>
    setServers(servers: Record<string, unknown> | undefined): Promise<{ added: string[]; removed: string[]; errors: Record<string, string> }>
    reconnect(name: string): Promise<void>
    toggle(name: string, enabled: boolean): Promise<void>
    readResource(name: string, uri: string): Promise<unknown>
    closeAll(): Promise<void>
  }
  ```
  Behavior:
  - **Fingerprint, never serialize**: an external entry's identity is `JSON.stringify([type, command, args, url, sortedHeaderEntries])`; a `type:'sdk'` entry's identity is its `instance` object. Unchanged = keep; removed = close; added = connect; changed = close + connect. Because `injectAll` builds fresh instances, every `setMcpServers` reconnects first-party servers — correct but cheap (in-process); document it.
  - **Attempt lifecycle**: each server record keeps `{client, transport, instance, abort, connectPromise, timer}`. `client.connect()` races `connectTimeoutMs`; on timeout/close/removal abort the record's `AbortController` (its `signal` is passed to `listTools` and `callTool`), call `client.close()` (kills the stdio child) and `instance.close()`, mark `failed`, never rethrow. `closeAll()` is idempotent, aborts in-flight attempts synchronously (so teardown never waits out a hung `listTools` page), then closes settled ones, and awaits the queue.
  - `type:'sdk'` entries: `const [a,b] = InMemoryTransport.createLinkedPair()`; `await instance.connect(a)`; `client.connect(b)`. Never connect the same instance twice (a second `connect` throws); on duplicate, treat as unchanged only when the identity matches.
  - `listTools()` follows `nextCursor` until exhausted; `inputSchema` is already JSON Schema — delete `$schema`. Tool identity: `fqn = mcpToolFqn(server, tool)` from Task 1; keep `rawName` for `callTool`.
  - `call`: await the queue, look up by FQN, `client.callTool({ name: rawName, arguments: args }, undefined, { timeout: toolTimeoutMs })`; join `type:'text'` blocks with `\n`, append `JSON.stringify(block)` for any other block, cap with the bash tool's head/tail (25 000 / 5 000; reuse/export `capToolText` from `tools/bash.ts`); `isError` when the result or a thrown transport error says so. Unknown FQN rejects with `unknown MCP tool: …`.
  - `needs-auth` classification uses `isMcpAuthError` (Task 2), not a message heuristic.
  - `statuses()` includes `tools` (bare names + description/annotations/`_meta`) so SettingsPanel's tool list and `useMcpApps` work; `source:'sdk'` for in-process, omitted for external; `config` = `{type, command, args, url}` only.
  - `readResource` → `client.readResource({ uri })`, forwarded unchanged.
  - `toggle(name,false)` closes and sets `disabled` (tools empty); `true` reconnects.

## Execution decisions (pre-flight review)

- **Tool names are sanitized, not passed through.** The Anthropic API requires `^[a-zA-Z0-9_-]{1,64}$`; a user-named server could otherwise 400 every request. One `mcpToolFqn` is shared by the model tool list, the registry/broker exemption and the client. Cost if wrong: MCP-Apps mapping for names containing invalid chars relies on the same function being used client-side (it is).
- **Entries are fingerprinted, never serialized.** `type:'sdk'` entries hold live instances and `JSON.stringify` throws; identity comparison is the only safe diff. First-party servers reconnect on every `setMcpServers` because `injectAll` builds fresh instances — accepted (in-process, cheap).
- **No prompt section for MCP tools.** The system prompt is frozen at create; guidance would re-register builtins and throw. Tool descriptions carry the model-facing information.
- **Connection barrier is per turn.** `whenReady()` is bounded by each server's 10 s connect timeout; a pending/failed server simply contributes no tools. Nothing blocks session create.
- **Status includes `tools` and never `env`/`headers`.** `args` is included despite occasionally carrying tokens (the CLI's own status does the same); the decision is explicit, not implied.
- **OAuth scope.** Stored OAuth servers refresh through `StoredMcpOAuthProvider`; a static `Authorization` header is dropped when a provider exists (native-only, via `preferAuthProvider`); refreshed tokens persist through `mcpStore.patch(name, { oauth })` + `flush()` — the field-scoped write preserves concurrent config edits and does not resurrect a deleted server, and the `patch` is what marks the store dirty (`flush()` alone no-ops). No live refresh integration test (unit coverage only).
- **Deferred:** MCP elicitation (servers receive method-not-found), `setMcpPermissionModeOverride` (501), `listTools` cursor pagination is implemented but untested (the in-memory and fixture servers do not paginate).
- **Create-failure teardown.** `NativeProvider.createSession` starts the connections before constructing `NativeSession` (whose constructor can throw on a corrupt/unsupported resume log); the constructor is wrapped in try/catch and a throw closes every connection (`mcp.closeAll()`). A hung *external* server on that path may still live up to `connectTimeoutMs` before the queued teardown closes it — bounded, not a leak.
- **MCP result text is never empty.** `call()` maps joined text blocks → `JSON.stringify(structuredContent)` → `'(no output)'`, because an empty text block is rejected by the Messages API on the next round (and persisted into the log).
- **Deferred residuals.** A re-authorization in Settings *replaces* the live store entry's `oauth` object; a still-connected session's later refresh can patch the stale object over it (self-healing: the rotated token yields `needs-auth`). The FQN template is not injective for names containing `__` (`('a__b','c')` vs `('a','b__c')`) — inherent to the `mcp__{server}__{tool}` convention the claude/CLI path already uses. `closeAll` sets `closing`, but `replaceAll` resets it, so a client mutation racing `destroy()` can reconnect; the manager's op lock and delete path make this unreachable in practice.

## Execution decisions

Final rulings from the P1.2 implementation review. Where this list and the
pre-flight list above differ, this one is authoritative.

- **API-safe FQN everywhere.** The model-facing name, the permission-broker
  name and the client's MCP-Apps mapping are all `mcpToolFqn(server, tool)`:
  `[^A-Za-z0-9_-]` → `_`, and anything over 64 chars is truncated to 55 + `_` +
  an 8-hex FNV-1a hash of the raw name. A user-named server can never make the
  API reject a request, and two names that sanitize to the same text stay
  distinct through the hash.
- **Fingerprint entries, never serialize them.** `type:'sdk'` entries hold a
  live server instance (circular, `JSON.stringify` throws), so identity is the
  instance itself; an external entry's identity is the JSON of its
  serializable fields (type / command / args / url / sorted headers, never
  `env` values). Replace compares identities and only reconnects what changed.
- **`preferAuthProvider` is opt-in.** The native path passes it so a stored
  OAuth provider owns auth and a grafted static `Authorization` header cannot
  shadow a refreshed bearer; the claude/SDK call sites keep their existing
  header-wins behavior (pinned by `server/mcp-config.test.ts`).
- **Per-record `AbortController` teardown.** Each server record bounds its
  whole connect task (handshake *and* every `listTools` page) and its in-flight
  tool calls. `closeServer` / `closeAll` abort synchronously before awaiting,
  so teardown never waits out a hung server and a timed-out connect closes the
  transport (killing a stdio child).
- **OAuth token persistence is field-scoped.** Refreshed tokens are written
  with `mcpStore.patch(name, { oauth })` followed by `flush()` — a wholesale
  `upsert` was rejected because the connection-time snapshot would revert
  later edits or resurrect a server deleted mid-session; `patch` inserts
  nothing for a missing entry and is what marks the store dirty.
- **No prompt section for MCP tools.** The native system prompt is frozen at
  create, and registering a section would also re-register builtins and throw.
  MCP guidance lives in the tool definitions (`promptOrder` starts at 200).
- **Deferred:** MCP elicitation (servers receive method-not-found),
  `setMcpPermissionModeOverride` (501), and integration coverage for
  `listTools` cursor pagination (the in-memory and fixture servers never
  paginate).
