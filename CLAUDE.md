# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A local browser UI for `@anthropic-ai/claude-agent-sdk`. Ships as a single `npx claude-react-web` binary that serves both the Hono API (port 3456) and the built React client. Sessions are backed by a pluggable **provider** layer (`server/providers/`); the default `claude` provider wraps a live SDK `Query` per session, so multi-turn conversations, interrupts, model switches, and permission-mode changes all drive an actual subprocess.

## Commands

```bash
npm install
npm run dev         # concurrently: tsx watch (server :3456) + vite (:5174, /api proxied)
npm run build       # build:client (vite → dist/client) then build:server (esbuild → dist/cli.mjs)
npm run typecheck   # tsc -p tsconfig.json + tsc -p tsconfig.node.json (both --noEmit)
npm run test        # vitest run (server unit tests + client hook tests)
npm run lint        # eslint .
npm run start       # run the built dist/cli.mjs directly
npm run preview     # build + start
```

Launch env: Anthropic credentials live in `~/.claude-react-web/config.json` (`authToken` / `baseUrl`), not env vars — `server/config.ts` reads no `process.env`; the server injects them into each SDK subprocess. The CLI warns at startup if `authToken` is unset. CLI flags: `-p/--port`, `--host`, `--token` (web access token; auto-generated on non-loopback host), `-o/--open` / `--no-open`, `--cwd`, `--model`, `--state-dir`, `--claude-binary`.

Two tsconfigs exist because the browser (`src/`) and Node (`server/`, `build.mjs`, `vite.config.ts`) have different `lib`/`types` needs; always run both when typechecking. Server tests run in Node; client tests run with **happy-dom** via `environmentMatchGlobs` in `vitest.config.ts` — first-match-wins, so the narrow `node` overrides (pure-logic `src/utils`, session-store reducers, styles, …) precede the broad `src/** → happy-dom` rule, and a file that needs jsdom's higher fidelity opts back in with a file-local `// @vitest-environment jsdom` pragma (`store.test.ts` does, for localStorage quota semantics). happy-dom over jsdom was measured, not adopted on reputation — the config comment carries the numbers. `setupFiles` points at `src/test-setup.ts`, which registers `afterEach(cleanup)` — `globals: false` means @testing-library/react's own auto-cleanup never self-registers, so without it every `render()` stays mounted past its test and an unmount-cancelled timer can fire inside vitest's DOM teardown (`ReferenceError: window is not defined`, exit 1 with all assertions green). Don't re-add per-file `afterEach(cleanup)`.

## Architecture

### Server: one provider session per tab

`server/session-manager.ts` is the core. It owns a pool of sessions, each backed by a **provider session handle** (`server/providers/types.ts` — `ProviderSessionHandle`) rather than an SDK `Query` directly. The default `claude` provider (`server/providers/claude/claude-provider.ts` + `claude-session.ts`) is the one that wraps the SDK `Query`; providers are registered in a `ProviderRegistry` (`server/providers/registry.ts`) and selected per session, so the manager itself is provider-agnostic. The `claude` provider advertises a `capabilities` set (supports interrupt / model switch / MCP / resume / fork / plugins / fast mode / effort level / …) that the manager guards control operations against.

For each session the manager holds:

- A provider handle exposing a queued input (`enqueueUserMessage` / `sendControlMessage` / `clearQueuedInput`) and a streamed `messages` async iterable. Under the hood the `claude` provider backs this with a `Pushable<SDKUserMessage>` queue (`server/pushable.ts`) whose `.iterable` is passed as `prompt` to `query({ prompt, options })`. User turns from HTTP `POST /sessions/:id/messages` are enqueued — via `send(id, text)` for plain text or `sendContent(id, content)` for multimodal (text + image) arrays.
- The provider's message stream. A background `pump()` task (`server/session-pump.ts`) iterates it, appends every message to a bounded history ring (`HISTORY_CAP = 500`), and fans out to all live WebSocket subscribers of that session. Ephemeral event streams bypass the ring entirely via early-`continue` (`prompt_suggestion`, and the `task_started`/`task_updated`/`task_progress` task-state stream — see `tasks-snapshot` in the frame list below). `system/thinking_tokens` is likewise ring-bypassed but still forwarded live (a transient thinking-token estimate the client mirrors into the WorkingBubble); `tool_progress` frames are dropped outright. Durable system frames outside the default allowlist must be added to `BROADCAST_SYSTEM_SUBTYPES` (`server/history-utils.ts`) — adding one there also makes it renderable from disk pages (history-reader's `isRenderable` reuses the set) and requires top-level payload passthrough in history-reader's `normalize()` plus a client unhide in `shouldHideByDefault` + a MessageList render branch. Currently allowlisted beyond the basics: `permission_denied` (non-interactive tool denial card), `informational` (loop text banners), `model_refusal_fallback` (refusal-fallback notice; its `retracted_message_uuids` — and assistant `supersedes` — drive eviction of the refused leg inside the client reducer's `applyMessage`, reusing the `EVICT_MESSAGES` machinery, so live replay and disk replay both evict), `local_command_output`, `memory_recall`, `elicitation_complete`, `api_retry` (rate-limit retry indicator — durable in the ring only so a reconnecting tab's incremental replay re-arms the client's transient slot), `task_notification`.
- A `pending` map of tool-permission requests (`PendingPermission`). The session registers a `canUseTool` callback (unless `permissionMode === 'bypassPermissions'`) that parks each request in this map, broadcasts on the permission channel, and resolves the SDK's promise only when the client POSTs a decision. The broker lives in `server/permission-broker.ts`.
- Two subscriber sets: one for messages, one for permission events. Each WebSocket connection gets its own queue+waiter iterable so a slow client can't block the pump.

Control operations (`interrupt`, `setModel`, `setPermissionMode`, `applyFlagSettings`) are delegated through the provider handle (guarded by its capabilities); the `claude` provider forwards them to `Query`'s methods, which implement them as in-band control requests to the CLI subprocess. The session holder also proxies `supportedModels`, `supportedCommands`, `supportedAgents`, `mcpServerStatus`, `getContextUsage` (again, capability-gated).

Stuck-session GC runs every 60s via `server/session-health.ts`. **Idle sessions are no longer auto-unloaded** — they persist until explicitly deleted by the user. The GC tick only catches sessions that are mid-turn (`pendingTurns > 0` or permissions pending) and have been silent longer than `workingStuckMs`: it auto-interrupts first, then escalates to a force-unload if the subprocess stays wedged (see `checkStuck`'s three cases: mid-turn silence, init-never-landed, and already-interrupted-escalation).

### Native provider: neutral vocabulary core + two boundary adapters

The `native` provider (direct Anthropic API, no CLI subprocess) is a host-free neutral core wrapped by two translating adapters — the shipped option C of the [provider seam neutralization](.agents/notes/implemented/architecture/2026-11-18-provider-seam-neutralization.md) note. The host stays SDK-shaped; only native's core is neutralized. `NativeProvider` implements `listResumable`/`getSessionInfo`/`renameSession` for the /resume picker and disk adoption: a durable log-only `session/title` event (latest-wins, fork-inherited) plus the host-side selective scan in `server/providers/native-resumable-listing.ts` give native full picker delete-recovery parity with claude ([decision record](.agents/notes/implemented/feature/2026-11-25-native-resumable-discovery.md)).

- `server/providers/native/vocabulary/` is the neutral frame language and the lift-out unit: `Message`/`ContentBlock`/`StreamChunk` + provenance, the durable `SessionEventMap` (the v3 log language), the live `AssistantFrame`/`OperationalFrame` union, constructors + the shared `BlockAssembler`, branded ids, and the identity facts (`FrameContext`/`defaultFrameContext`/`Usage`). It imports ONLY neutral `shared/*` + Node builtins + sibling vocabulary.
- The core (`loop.ts`, `native-session.ts`, `subagent.ts`, `task-manager.ts`, `tools/`, `session-log/`, replay) speaks only the vocabulary: neutral turn engine, neutral v3 log append/flush/migrate, neutral model-history replay, neutral emission. The core WRITE path appends neutral v3 events directly; the writer's legacy-input migration serves reading/migrating legacy logs and the writer's v1/v2 compat contract, not core writes.
- Host adapter (SDK allowed): `server/providers/native-host-frame-adapter.ts` (`wrapNativeCore` implements the SDK-shaped `ProviderSessionHandle`; neutral frames/events ↔ `AgentMessage`; input identity, lease callbacks, `copyConsumedAt`/`projectFileBlocksForProvider`), with adapter-side siblings `native-frames.ts` (legacy SDK frame builders, tests), `native-subagent-transcript-source.ts` (host transcript source), and `native-provider.ts` (composition root implementing `AgentProvider`, wiring core → `wrapNativeCore`).
- Wire adapter (API projection): `native/wire/wire-projection.ts` + `native/attachment-projection.ts` project neutral model history → the Anthropic API request (tool_result grouping, raw-JSON tool args, signed-thinking filter, file/PDF projection).
- Persistence: native logs are v3 neutral `SessionEvent`s; v1/v2 logs migrate losslessly eager-at-open (uuid/seq/thinking-signature/attachment-blockPath preserving; temp+fsync+rename). The host history read path projects neutral events → SDK `RawLine`s through the adapter seam (`projectNativeEventToSdkLine`) before the renderable filter. Read-side neutrality is complete: core read consumers (agent-profile/usage/skill, attachment index, PDF budgets, occurrence/catalog scans, fork seeds) read the canonical neutral events via `neutralEventsOf`/`neutralFileOccurrences`; a v3 log maintains no live legacy read view (`log.events` is the v1/v2 list only, `append` returns the neutral event), and `projectNeutralEventToLegacy` survives only for the writer's v1/v2 write-compat, the host seam and the migration round-trip pin.
- Auto-compact: native auto-compact retains pre-compact history visible (claude-style `compact_boundary` divider + `isCompactSummary` card). It is an append marker, not a transcript reset — the provider appends a `retainHistory`-fenced `session/compact` event and floors only the MODEL history (`historyFromEvents` still floors at the last compact of either kind), while the manager appends the divider + summary to the retained ring/seq space (no `session-cleared`, no generation bump). The renderable read paths (page/entries/search/reconcile snapshot) keep pre-compact history above the marker; the forward `retainHistory` fence leaves legacy compacts floored. One `summaryUuid` shared by the live summary frame and the disk-synthesized summary dedupes to a single card on restart and crash recovery.
- Compact summary input: native in-place compact (auto AND manual `/compact`, shared `runInPlaceCompact`) summarizes the provider's AUTHORITATIVE model history via the optional handle method `getCompactionInput()` — the SDK projection of native's uncapped `historyFromEvents` model history, floored at the last compact, model-visible only (sidechain internals excluded; subagent RESULTS remain as main-history tool_results), so ring eviction can never starve the summarizer of the previous summary or early post-compact content. The neutral core exposes `getCompactionHistory(): RequestMessage[]` + `getCompactionBoundary()`; the host adapter's `projectCompactionInput` owns the SDK projection and recovers the floor identity (the previous summary marked `isCompactSummary` so recap keeps it as a full-text System line; the context snapshot dropped — compaction metadata, not a human turn). Providers without the method fall back to the capped ring slice (`ringSliceForCompact`); `/handoff` + plugin-compact keep the full merged ring. Compact image refs are hydrated to verified base64 before the summary API call (`buildCompactAttachmentContent` reuses `resolveImageBlocks`, the send path's single verification point, fail-closed) — base64 exists only in that request copy, never the rings.
- Structural pins: `native/vocabulary/neutrality.test.ts` bans SDK/`agent-message`/host-frame-vocabulary imports (value AND type-only) in core production files, pins vocabulary purity, asserts the adapters are the sole boundary importers, and pins the neutral `data:` envelope on core append literals; `native/host-free.test.ts` bans host-domain service imports (the six-port discipline). The SDK package stays a dependency of the host/claude/adapter, never of native core.

### WebSocket + REST wire protocol

The server uses a single WebSocket connection per browser tab (`server/ws.ts`) that multiplexes all channels. The canonical frame definitions live in `shared/ws-protocol.ts` (generic); `server/ws-protocol.ts` and `src/ws-types.ts` are thin instantiation aliases that bind those generics to the server's SDK types and the browser's lightweight types respectively — **not** duplicated mirrors. The client connects via `useWsHub` (`src/hooks/useWsHub.ts`) which provides exponential backoff, ping heartbeat, and ref-counted subscriptions.

**WebSocket frame kinds** (server → client) — canonical list in `shared/ws-protocol.ts`:

- `sessions-snapshot` / `session-created` / `session-update` / `session-removed` — global session list mutations
- `replay` / `replay-done` / `message` — per-session message stream (replay on subscribe, then live)
- `subscribe-result` — the server's answer to one `subscribe` frame: `{ ok, reason: 'served' | 'already-live' | 'starting' | 'refused' | 'closed' }`, the STATE of this connection's per-session channel (the prose `error` frame keeps the message). Exactly one per accepted subscribe, so the client never infers channel liveness from ambient frames. `already-live` also RE-SERVES the replay (a listener may have attached after the first one); a `closed` result is emitted when a channel ends (unload / sleep / terminate), which is the only per-connection signal for that
- `message-consumed` — the SDK has read a queued user turn (drives the "sending → sent" transition). The live frame only serves already-attached tabs; the durable half is `consumedAt` on the ring entry itself, which `dispatchUserMessage` (idle direct hand-off, stamped before the broadcast) and `onInputConsumed` (queue-shift, stamped by a tail scan of `history`) keep in sync. Both are required: a ring entry with `receivedAt` but no `consumedAt` replays as permanently 'queued' on any client without a cached transcript
- `messages-withdrawn` — queued user turns were withdrawn by an interrupt with `cancelQueued` (host input-queue drain + SDK `interrupt_cancel_queued_v1`); the server removed them from its replay ring and live tabs evict the matching bubbles via the `EVICT_MESSAGES` reducer action. The withdrawal set is restricted to still-unconsumed `promptUuids` entries (`c == null` — the consumption fact stamped by `onInputConsumed`), so control messages riding the input queue (compact hand-off seed), CLI-internal uuids, and prompts the SDK already took are never evicted, and the matching unconsumed ledger entries are pruned so the interrupt dead-state heal probe reads idle. The session remembers a capped withdrawal window (`withdrawnUuids`) and seeds every NEW msgstat subscriber with one synthetic frame — a tab disconnected during the stop heals on reconnect, since incremental sinceUuid replay can never re-send ring-removed messages. Rides the same per-session input-queue-status channel as `message-consumed`
- `permission-request` / `permission-resolved` — per-session tool permission events
- `elicitation-request` / `elicitation-resolved` — per-session MCP elicitation (OAuth) events
- `dialog-request` / `dialog-resolved` — per-session user dialogs (`Options.onUserDialog`, currently `refusal_fallback_prompt`). The resolved frame carries `retractedMessageUuids`; every tab evicts those messages from its transcript store via the `EVICT_MESSAGES` reducer action on receipt
- `session-cleared` — a `/clear` completed and the server truncated its history ring; clients reset their transcript store
- `global-permission-request` — cross-session permission notification (for sidebar badge)
- `cli-notification` — a CLI notification frame (SDK `system/notification`: "waiting for your input", idle nudges) narrowed by the pump (`cliNotificationOf`, early-continue — never the ring or message channel) and mirrored onto the global channel so App-level code fires a browser/OS notification even when the session's panel isn't mounted. Client-side it routes through `useSessionNotifications.maybeCliNotify` (same three-state skip/toast/desktop dispatch as permissions, but transient: CLI-suggested timeout clamped to 2–30s, low/medium priority silent on desktop, `key`-tagged dedup)
- `update-info` — update-checker snapshot on the GLOBAL channel (always-on, seeded on every new connection). The update-info hub (`server/update-info-hub.ts`) publishes whenever a meaningful snapshot field changes (`latest` / `deprecated` / `error` / `updateAppliedToDisk` / `disabled`), regardless of trigger — the periodic scheduler (`server/update-schedule.ts`, `config.updateCheckIntervalMs`, default 12 h), a manual Check now, an in-app install completion, or a registry-disabled reset. The client merges frames into `useUpdateInfo` with a `checkedAt` staleness fence, preserving the GET-only CLI/SDK overlays
- `context-usage` — per-session context window usage
- `prompt-suggestion` — predicted next-user-prompt pushed after each turn when the SDK's `promptSuggestions` option is on (default). Ephemeral: it bypasses the history ring entirely (pump early-`continue`s on `prompt_suggestion` messages), rides a dedicated psug channel mirroring context-usage, and is cleared client-side when the user sends a message or the transcript is cleared
- `tasks-snapshot` — full background-task list snapshot (server-side `session.tasks: Map<taskId, TaskRecordUi>`, `shared/tasks.ts`). The pump folds SDK `task_*` system frames via `applyTaskEvent` (`session-pump.ts`, unit-tested): `task_started`/`task_updated`/`task_progress` are ephemeral (early-`continue`, never ring, never the message channel) and only ride this dedicated channel; `task_notification` ALSO folds state but keeps the ring+broadcast path (the client reducer's async-subagent completion branch matches on it) and cancels the matching subagent watcher via the `onTaskNotification` pump dep. The watcher itself seeds a `TaskRecordUi` (taskId = agentId) for background Agent dispatches the CLI sends no frames for, and its synthesized notification folds the seed to terminal. Terminal records are capped at 50 (oldest evicted). `TaskRecordUi` carries `result` from the harness `<task-notification>` injection's `<result>`, a foreground shell's matching `tool_result`, or a background completion's `output_file` (read by the pump before the fold). Before initial subscription or live task fan-out, the task broadcaster runs `projectTasksSnapshot` once: small results stay inline, large results omit `result` and carry `resultRef` metadata, while live records and the sidecar keep full strings. Partial previews are lifecycle evidence/view-local summaries only, never richer canonical results in `activeSubagents`. If the projected roster exceeds 256 Ki chars, `frame-bridge` emits bounded `tasks-snapshot-chunk` JSON fragments instead of dropping metadata; the client joins one baseline before dispatching `TASKS_SNAPSHOT`. injection frames are hidden from the transcript (`shouldHideByDefault` via `classifyTaskNotificationInjection`): foldable ones (they carry a `<tool-use-id>` and render in the TasksPanel) and payload-less ones alike — the harness's resume-time "didn't finish before the previous session ended" notice is status-only and has no `<tool-use-id>`, so it would otherwise surface as raw XML. A result-bearing injection with no `<tool-use-id>` (a background agent's re-notification after a resume) folds into the task record keyed by its `<task-id>`, CREATING a terminal subagent record when none exists (the original was evicted by the terminal cap or never seeded; the created record keys the disk transcript by taskId/agentId, so it needs no toolUseId) — and `buildTranscriptRows` drops its raw-XML row only when the record holds THIS payload (`taskResultVersions` from `mirror.tasks`: the record's result content-generation, inline or `resultRef.resultVersion`, equals the injection result's — so live and sidecar replay agree, and a record holding a different/older report never hides an unfolded one); a mismatched result or a monitor `<event>` injection keeps the neutral card so the payload is never silently dropped. `TaskResultStore` (`server/task-result-store.ts`) persists `session.tasks` per session so results survive a restart. The client's `TASKS_SNAPSHOT` reducer action also enriches matching `activeSubagents` (taskId/progressSummary join by toolUseId; `isBackgrounded` flips 'running' → 'background'). `TASKS_SNAPSHOT` is the SINGLE authority for a subagent's `isAsync` (async/sync badge truth): it writes `task.isBackgrounded` for both true and false, on live and terminal records. `task_notification` is a pure completion signal for ALL subagent tasks (async and foreground — the CLI emits one for foreground agents too), so it never stamps `isAsync`; launch-ack tool_results are skipped by a pure-regex guard (never settled as results), and a `running` record is only deferred to `pending` at turn end when `mirror.tasks` still lists a live backgrounded task
- `session-recap-update` — a recap state transition (pending / ready / error / cleared) for this session
- `hook-run` — a hook lifecycle event fired during the turn
- `commands-changed` — the supported slash-command set changed (e.g. after dynamic skill/command discovery)
- `git-snapshot` — work-tree git status snapshot (status / branches / stashes inline), computed once per repoGroup (`gitGroupKeyOf`: `repoRoot ?? cwd`) after any filesystem-mutating event and fanned out to all sessions in the same group; new subscribers are seeded with the most recent frame. Client hooks `useGitStatus` / `useGitBranches` / `useGitStashes` are pure sinks (mount HTTP fetch once + manual refresh preserved; frame arrival replaces state directly, zero refetch). diff / log remain on-demand fetch
- `terminal-snapshot` / `terminal-output` / `terminal-state` — the per-session embedded-terminal channel (see **Embedded terminal** below). Ephemeral: never enters the history ring or the message channel. `terminal-snapshot` is the attach/resync seed (serialized headless screen + generation + seq + state); `terminal-output` carries raw PTY chunks with a monotonic per-generation seq; `terminal-state` marks spawn/exit/close transitions. Unlike the message channel, `terminal-subscribe` does NOT emit `subscribe-result` — the snapshot frame IS the seed/ack (the hub folds `subscribe-result` into the message channel's liveness, so a terminal one would pollute it; the subagent channel follows the same rule)

`server/routes/index.ts` (`buildApiRouter`) composes the REST surface under `/api` from per-concern sub-routers in `server/routes/` (`sessions.ts`, `permissions.ts`, `uploads.ts`, `image-uploads.ts`, `recap.ts`, `config-routes.ts`, `health-routes.ts`, `mp-marketplace.ts`, `git-write.ts`, `update-routes.ts`, `search.ts`, `skills.ts`, `hooks.ts`, `dialog.ts`):

- `GET /sessions`, `POST /sessions`, `DELETE /sessions/:id`
- `POST /sessions/:id/messages` — accepts either legacy `{ text }` string or `{ content }` array (text + image + file blocks for multimodal input). Image blocks come in two shapes, both accepted forever (mixed model): the durable ref `{ type: 'image', attachment: ImageAttachmentRef }` (`shared/image-attachment.ts`; `id: 'sha256:<64hex>'` + mediaType/bytes/width/height) and the legacy `{ type: 'image', source: { type: 'base64', data, media_type } }`. Total base64 payload capped at 28 MB (ref blocks add nothing to it); the client caps raw image bytes at 20 MiB so the encoded form fits (both in `shared/upload-limits.ts`). Valid image types: jpeg, png, gif, webp. File blocks use `{ type: 'file', attachment: { id, name, size, digest? } }` (≤20 per message): the route resolves the id against the upload registry, replaces it with the canonical ref, and hands `ResolvedFile` paths to `SessionManager.sendContent`. Uploads are content-addressed: one immutable object per sha256 under `<stateDir>/claude-web-attachments/v1/`, a read-only hard-link alias per (digest, name), and a registry keyed by upload `id` with a `digest` index (identical bytes/name dedupe to one alias; each owning session keeps its own entry). `getById` also accepts a future `sha256:<digest>` reference through that index. Legacy `claude-web-uploads/` entries stay readable and get a boot-time digest backfill; content reads verify the bytes first (≤8 MiB pre-verified, larger stream-and-abort), and deletion unlinks the alias/object only after its last reference. The model's own `Read` of the alias path bypasses that verification. The ring/broadcast keeps the public structured FileBlock without registry path or native model metadata. Claude projects each file to the deterministic handle text in `shared/upload-handle.ts`; native persists a v2 canonical occurrence and re-projects it on every API round as either a native handle or a verified PDF `document` (base64 exists only in that request copy, never the log or browser). Native `AttachmentRead` uses the same registry/log/digest authorization for bounded text and PDF tool results. Upload deletion also returns 409 while any live/dormant native log, fork or compact handoff references the id, or an in-flight send holds its lease. Scheduled sends reject file blocks.
- `POST /api/uploads/images` + `GET /api/attachments/images/:digest` (from `server/routes/image-uploads.ts`) — the durable image-reference pipeline. The composer uploads each already-normalized blob as a raw body; the route inspects the actual bytes (`shared/image-inspect.ts`), enforces the shared byte/pixel/dimension limits, and publishes via `AttachmentObjectStore.publishImage` into a SEPARATE `images/<digest[0..1]>/<digest>` tree under `<stateDir>/claude-web-attachments/v1/` (plus a `.json` meta sidecar) — no filename alias, no upload registry: the digest is the identity, equal bytes dedupe to one object, and publication reuses the file store's staging→fsync→hard-link→`0o400` writer (`publishObjectCore`). Image refs are GLOBAL to the authenticated local server (no session ownership check) and there is NO GC (retention-neutral; deleting an object would break ref-based rendering). The content route verified-reads (digest + length) before serving, with the sidecar's Content-Type and an immutable private cache; missing → 404, corrupt → 500, malformed digest → 400. `sendContent` verifies every ref fail-closed through `resolveImageBlocks` (`server/attachment-resolver.ts` — the single verification point, reused by scheduled sends) BEFORE dispatch, and keeps the public ref block in the ring/broadcast/seq store/sidecar; base64 exists only in the SDK copy. `projectImageBlocksForSdk` (`server/session-manager.ts`) projects each ref at dispatch (idle hand-off, queued materialization, crash recovery) into a deterministic handle text block (`shared/image-handle.ts` `imageHandleText`/`parseImageHandle`, full 64-hex digest in both identity slots) followed by the base64 SDK image block — the SDK JSONL stays base64 and the model gets a read-only path. Disk reads recover refs in history-reader's `normalize` (`recoverImageRefBlocks`: a fully parsed handle + the adjacent base64 image → ref block); resume/fork/side-chat ring seeds prefer the sidecar's public content by uuid, else parse the handle (`projectSeedImageRefs`); rows with neither keep legacy base64 verbatim.
- `POST /sessions/:id/interrupt`, `/model`, `/permission-mode`, `/settings`
- `POST /sessions/:id/thinking` — set extended-thinking config (`{type:'adaptive'} | {type:'disabled'} | {type:'enabled', budgetTokens}`). Spawn-time rides SDK `Options.thinking`; the live switch maps to `Query.setMaxThinkingTokens` (adaptive→null, disabled→0, enabled N→N — there is no Settings key for thinking) via the provider handle, capability-gated on `supportsThinkingControl`. Bare `{type:'enabled'}` is accepted at create but rejected 400 live (not expressible as a token count). Persisted on `SessionMeta.thinking`, so resume/fork/clear/respawn re-apply it at spawn; `thinkingSupported` (keyword-classified in `effort-capability.ts`) hides the client chip on non-thinking models.
- `GET /sessions/:id/tasks/:taskId/result?runId=&offset=&limit=` — bounded task-result pages (UTF-16 offsets, max 128 Ki chars). Live task state is authoritative with no stale-disk fallback; dormant/slept/terminated sessions read the existing task-result sidecar without resuming. Run mismatches fail explicitly.
- `POST /sessions/:id/tasks/background` — background in-flight foreground tasks (CLI Ctrl+B semantics; optional body `{ toolUseId }`); `POST /sessions/:id/tasks/:taskId/stop` — stop a running background task. Both delegate through the provider handle, capability-gated on `supportsTaskControl`. `agentProgressSummaries` defaults to on in the claude provider (feeds `task_progress.summary`)
- `GET /sessions/:id/context-usage` `/models` `/commands` `/agents` `/mcp-status`
- `GET /sessions/:id/usage` — structured `/usage` data (session cost/token totals + claude.ai plan rate-limit windows); `GET /sessions/:id/account` — authenticated-account info (email / org / subscription / auth backend, SDK `accountInfo`, narrowed via `shared/account-info.ts`, capability-gated on `supportsAccountInfo`). Both live-Query-only control reads; the client pulls them together in `useSessionUsage` and renders them in the SettingsPanel Usage tab (`UsagePanel`).
- `POST /sessions/:id/rewind-files` — restore files to their state at a user message via the host-managed shadow-repo snapshot sidecar (replaces the former SDK `Query.rewindFiles` path; no live Query required). Body `{ messageId, dryRun? }`: `messageId` is the app-level user-message uuid. `dryRun: true` previews the diff without touching files. Works offline — dormant and terminated sessions can rewind; only real (non-dry) rewinds are blocked while the session is `working` (409; dry-run is still allowed). Restores tracked files to the snapshot state and deletes files that were created after the message. A real (non-dry) rewind fires `git-snapshot`. Result narrowed via `shared/rewind.ts`. Requires a git-based cwd (non-git sessions are unavailable). Client entry: right-click a user message → "Rewind files to this message" → ConfirmDialog showing the dry-run diff. Conversation truncation is the separate discard feature; the two compose.
- `GET /sessions/:id/file-snapshots` — snapshot sidecar capability: whether snapshots are available for this session (`available: boolean`, `reason?: 'disabled' | 'no-snapshot' | 'not-git'`) plus the list of rewindable anchors (`anchors: Array<{ messageId }>`). Does not require a live Query — reads the sidecar directly. 404 for unknown sessions.
- `GET /sessions/:id/history?before=&beforeUuid=&limit=` — disk-paged history (lazy-load older messages, offset semantics: `before` = previous response's `startIndex`, `beforeUuid` = first-page anchor on a disk-stable uuid). Served through the JSONL parse cache (`server/jsonl-cache.ts`): freshness keyed on `(size, mtimeMs)`, appends parse incrementally, entries LRU-capped at 4 sessions (`history_cache_hit` / `history_cache_miss_full` / `history_cache_miss_incremental` metrics).
- `GET /sessions/:id/snapshot-diff?from=<messageId>` — structured diff from a recorded snapshot anchor to the current worktree capture. Returns `{ diffs: Array<{ file, status, additions, deletions, patch? }> }`. Requires the snapshot sidecar to be available; 400 when the anchor is missing or snapshots are disabled. Does not require a live Query.
- `GET /sessions/:id/file-search?q=&limit=` — composer @file/@folder candidate search (`server/file-search.ts`). Live OR dormant (needs only `meta.cwd`, no Query). Git-first (`ls-files -z --cached --others --exclude-standard` — .gitignore respected, untracked-non-ignored included) with a bounded fs-walk fallback for non-repo / git-failure cwds; a trailing `/` on `q` switches to live `readdir` of that directory (the picker's drill state). Fuzzy rank (exact > prefix > substring > subsequence, directory bonus), ≤20 results, `\` normalized to `/`, `..`-segment / absolute queries rejected outright, every result containment-checked AND mention-expressible (`isMentionExpressible` — embedded-quote / control-char filenames are filtered because the mention grammar cannot serialize them). Never reads file contents.
- MCP on a live session: `POST /sessions/:id/mcp/servers` adds/removes dynamic MCP servers (SDK `setMcpServers`). It accepts the **same two inputs as `POST /sessions`**: `enabledMcpServers` (string[] of global server names resolved from `McpConfigStore`) and/or `servers` (inline `McpServerConfig` map, which wins on name collision). Both are run through `SessionManager.mergeMcpServers` before reaching the SDK, so the dynamic path can reference globals by name. `setMcpServers` has **replace** semantics over the dynamic set, so the merged map must list every dynamic server that should stay connected; an empty result clears them all. `enabledMcpServers` must be a `string[]` (validated on both routes — a stray string is a 400, not iterated char-by-char). Per-server control: `POST /sessions/:id/mcp/:name/reconnect`, `POST /sessions/:id/mcp/:name/toggle`.
- `POST /sessions/:id/permissions/:pid/decide` — `{ behavior: 'allow' | 'deny', persistForSession?, message? }`. Allow paths always echo the original `input` as `updatedInput` (the SDK's runtime Zod schema requires it even though the TS type marks it optional). `persistForSession: true` rewrites every SDK-provided suggestion to `destination: 'session'` so the allowance is Query-scoped, not user-settings-scoped.
- `POST /sessions/:id/fork` — duplicate a session (resumes from the fork point)
- Scheduled sends (server-side, in-memory — NOT persisted across restarts): `POST /sessions/:id/schedules` `{ fireAt, text | content }`, `GET /sessions/:id/schedules`, `DELETE /sessions/:id/schedules/:scheduleId`. A ~1s ticker fires due sends through the same `sm.send`/`sm.sendContent` path as `POST /messages`; body validation is the shared `server/send-body.ts` helper used by both routes. Image ref blocks ride verbatim and are verified at fire time by the same `sendContent` resolver; a missing/corrupt image marks the schedule `failed` (no retry). A session reaching fire time terminated/dormant/deleted is marked `failed` (never auto-resumed). Session deletion (observed via the global `removed` feed) drops that session's schedules. Client UI: a clock button beside Send opens a time picker; pending sends render as countdown chips above the composer (`src/hooks/useScheduledSends.ts` poll-reconciles; no WS frames).
- `GET /sessions/:id/dialogs` and `POST /sessions/:id/dialogs/:did/decide` — pending user dialogs (`Options.onUserDialog` / `supportedDialogKinds` pipeline, mirrored on elicitation). `supportedDialogKinds` is hardcoded to `['refusal_fallback_prompt']` (see `shared/user-dialog.ts`); unknown kinds are short-circuited to `{behavior:'cancelled'}` server-side. Decide body: `{ behavior: 'completed', result }` (result ∈ `retry_fallback | edit_prompt | cancelled` for the refusal-fallback kind) or `{ behavior: 'cancelled' }`. The `onUserDialog` + `supportedDialogKinds` pair must always travel together (spawn, resume, respawn) — non-empty kinds without a callback make the SDK spawn throw.
- `POST /sessions/:id/recap` — AI-generated session summary
- `/api/fs` (from `server/fs-routes.ts`) — minimal directory-only browser used by the cwd picker. Lists sub-directories of an absolute path; never returns file contents.
- `/api/git/*` (from `server/git-routes.ts`) — read-only `GET /status`, `/diff`, `/log`, all `?cwd=…`-scoped. Returns `{ isRepo: false }` (200) when the cwd is reachable but isn't a work tree. Writes live under `/api/sessions/:id/git/*` (in `server/routes/git-write.ts`): `stage`, `unstage`, `discard`, `commit`, `abort-merge`, `abort-rebase`, `stash`/`stash-pop`/`stash-drop`, `branch`, `checkout`, `session-files`, `session-diff`, `commit-message`. Destructive verbs require `confirm: true` in the body. After every write the route broadcasts a `git-snapshot` and returns the freshly-fetched `GitStatus` (and `branches` / `stashes` when relevant) so clients update without a second round-trip.
- Disk-backed stores, each mounted as its own router and persisted under the state dir: `/api/mcp-config/*` (global MCP server config, `mcp-config.ts`), `/api/mp/*` (homegrown git-repo marketplace — `mp-store.ts`; enabled entries are injected into `Options.plugins` on spawn, so it's the plugin path), `/api/snippets` (composer text macros, `snippet-store.ts`), `/api/ui-state` (session groups + sidebar order, `ui-state-store.ts`). `/api/update-info` (in-app upgrade check, `update-routes.ts`; POST /update is 400-gated on the desktop host). Periodic checking: `config.updateCheckIntervalMs` (default 12 h, 0 disables) drives a generic completion-based scheduler (`server/update-schedule.ts`, DSH semantics: backoff ×2 capped, ±20% jitter, coalescing) in two instances — the web host's npm probe (`startUpdateSchedule`, armed in `cli.ts` after the startup probe; ticks read live config) and the desktop feed check (`desktop/updater.ts`, skips ticks while an offer is busy). Every meaningful checker-snapshot mutation publishes through `server/update-info-hub.ts` (keys: latest/deprecated/error/updateAppliedToDisk/disabled) — scheduled probe, Check now, install completion, or disabled reset alike — and rides the always-on `update-info` global frame; the client merges with a `checkedAt` fence (`src/utils/update-info-merge.ts`). Notification is three explicit states, no ✕ on the nag: Update / Remind me later (stateless close — per-mount dedup only, reload re-nags) / Skip this version (persistent: localStorage web, `desktop/update-skip-store.ts` desktop); a failed desktop download re-offers next tick. Decision record: `.agents/notes/implemented/feature/2026-11-24-update-check-subsystem.md`; `/api/search` (message search across a session); `/api/sessions/:id/skills` and `/api/sessions/:id/hooks` (skill policy + hook config per session, backed by `shared/skills.ts` / `shared/hooks.ts`).
- `GET`/`POST /api/config/web-import` (from `server/routes/web-import.ts`, **desktop host only**) — the desktop-onboarding "import from the web version" pre-screen (`src/components/SetupWebImport.tsx`, rendered by `SetupPage` as an early return before wizard step 0, and **skipped outright** — straight to step 0 — when the probe reports `exists: false`, i.e. none of the three portable files is present in the source dir, so a user who never ran the web build never sees the step; the skip keys on the server's `exists` and NOT on "no section errors", since a missing source `config.json` makes `credentialsError` fire in exactly that ordinary case). It is a **read-only** layer over the web build's state dir (`server/web-import.ts`, `~/.claude-react-web` by default) that reuses the readers' own coercion (`coerceProfileEntries` / `resolveActiveProfile` / `McpConfigStore` / `MpStore` with `readOnly: true`, so a stale manifest cache on the web side is returned as-is instead of being self-healed) rather than reimplementing a parser. `GET` enumerates the three portable artifacts as one frame with **per-section failure isolation** — a corrupt `config.json` / `mcp-config.json` / `marketplaces.json` only collapses its own section to `*Error` + an empty list, never a 500 — and secrets never cross the wire (MCP rows carry `envKeys`, not values; the token is `maskToken`'d; and credentials embedded in a URL are masked to `user:***@` — the marketplace source URL, an MCP server's remote `url`, its `command` text and its `importErrors` text — with the secret taken as everything after the **first** `:` of the userinfo and the userinfo ending at the **last** `@` still inside the authority, so scheme/host/path stay readable and a path `@` is untouched). `POST` copies the selected subset: credentials into the **active** profile (same heal + raw-index selection as `/config/setup`; a field the source lacks is left untouched), MCP servers by name (same-name skipped, validation failures isolated per item — deliberately without the source's `oauth` block, whose `redirectUrl` is host-specific), marketplaces by copying the source's clone dir to `cloneDirFor(id)` via a `<target>.importing` staging dir + rename, carrying `enabledPlugins`. Each section returns `{ imported, skipped, failed }`, and `credentials.configured` mirrors `GET /config`. On the screen the three kinds are labelled sections; a row's checkbox only builds a reversible **selection** (unticking before the write is a full revert), `Import selected (n)` performs the write, the bulk button is a **toggle** — `Select all importable`, flipping to `Clear selection` once every importable row is ticked (one button, not two; three is already tight) — and the hand-off to the wizard's finish path happens on the **leave button**, never on an import, because a tick means "import this one thing" (a tick that ended the flow was the recorded acceptance defect; the button is deliberately not labelled `Next`, which read as "continue with what I ticked"). That leave button is labelled by state: **`Finish`** once an import on the screen has configured the server (the wizard's own last-step word — a user who just imported credentials saw an unchanged screen and no idea what to press), **`Skip`** otherwise.

The `host: 'web' | 'desktop'` option is threaded explicitly — `ServerContextOptions.host` (`server/bootstrap.ts`, defaults `'web'`) → `AppOptions.host` (`server/app.ts`) → the last-but-one positional argument of `buildApiRouter` (`server/routes/index.ts`). It exists because "desktop vs web" is a real deployment axis (state-dir layout, no TCP bind on the desktop host) and is **not** inferred from `bind` being absent: `bind` being web-only is a current accident, not a contract. Routes that only make sense on one host are mounted conditionally on it.

`server/app.ts` composes the Hono app: a web-access auth gate (no-op unless bound non-loopback or a token is set), CORS (reflects trusted/loopback/LAN origins only), a 32 MB body limit, security headers, request logging, then the API/WS routers and static client serving. It also mounts the per-store routers (`/api/mcp-config`, `/api/snippets`, `/api/ui-state`) only when their stores were provided, and locates the built client by walking a few candidate paths so both `tsx server/cli.ts` and the bundled `dist/cli.mjs` find `dist/client/` without config.

### Git integration

`server/git.ts` is the single owner of git execution. Every git invocation goes through `runGit(cwd, args, opts)` which uses `child_process.execFile` (never a shell) with a fixed argv; user-supplied paths are validated by `validateRepoRelativePath` (rejects absolute paths and `..` segments) AND prefixed with `--` so a path that happens to look like a ref (e.g. `HEAD`) cannot be reinterpreted. Diff bodies cap at `MAX_DIFF_LINES = 500`, `MAX_DIFF_BYTES = 256 KB`, and `MAX_DIFF_LINE_CHARS = 2000` (whichever binds first; `truncated: true` then set) — the preview contract, so a minified/lockfile diff can never freeze the panel; `GET /api/git/diff?full=1` (and `/diff-range-file?full=1`) returns the complete body for the client's "View full diff" hatch. The AI commit-message diff caps at `MAX_AI_DIFF_BYTES` (head+tail trim with an elision marker). `getStatus` probes `isInsideWorkTree` and falls back to `{ isRepo: false }`; `getStatusInRepo` is the variant for callers that already validated repo-ness (write routes use this to avoid a redundant `git rev-parse` spawn per write). Exception: `server/snapshot/shadow-git.ts` and `server/snapshot/snapshot-service.ts` execFile git directly for `--git-dir` shadow-repo operations with their own stdin pathspec helpers; they still never use a shell.

Each session gets a `gitStartSha` anchor when it spawns inside a work tree (`tryCaptureGitHead` — null for unborn HEAD, sessions outside repos, or detached states with no SHA available). It's persisted alongside `SessionMeta` and preserved across resume / fork. Three routes hang off it for the GitPanel "This session" view: `session-files`, `session-diff`, `commit-message` (the AI button). When `gitStartSha` is null those routes return empty payloads / 400 — the UI hides the section.

`server/git-broadcast.ts` debounces `git-snapshot` broadcasts per repoGroup. The pump (`server/session-pump.ts`) detects mutating tool_use blocks (`MUTATING_TOOL_NAMES = {Edit, Write, NotebookEdit, Bash}`) by id, and when the matching tool_result lands it calls `scheduleGitBroadcast`. Debounce timing is keyed by **repoGroup** (`gitGroupKeyOf`: `repoRoot ?? cwd`), so bursts of edits across sessions sharing the same repo collapse into a single status computation. `broadcastGitStatusChanged` pushes a complete `git-snapshot` frame and fans it out to all sessions in the group. User-initiated POST writes pass the already-computed fresh status list as `opts.snapshot` to avoid a redundant git spawn. `cancelGitBroadcast(this, id)` on session unload only clears the timer when the triggering session is the origin and no peer in the same group remains alive; otherwise the origin yields to the surviving peer. `getStatusCached` has been removed — the herd-effect stampede it guarded against is eliminated by the snapshot-push design.

`server/anthropic-api.ts` (`callAnthropicMessages`) is the shared Anthropic Messages caller used by both `recap.ts` and `commit-message.ts` — same auth header shape, version pin, 15s timeout. Each caller does its own post-processing (recap strips JSX fragments; commit-message strips code fences) but the wire layer is one place.

Client-side: `src/components/GitPanel.tsx` is a per-panel overlay (mounted alongside `SettingsPanel` inside `Chat`, dismissed by backdrop / Escape, has higher keyboard priority than Settings). `ChatPanel.tsx` renders an always-visible header chip showing branch + dirty/ahead/behind/conflict at a glance; clicking it opens the panel. Hooks are split: `useGitStatus` (status, with WS auto-refetch + a JSON-string no-op compare so unrelated tool runs don't cascade renders), plus `useGitDiff` / `useGitLog` / `useGitBranches` / `useGitStashes` / `useSessionFiles` (lazy-fetched per accordion). Writes go through `useGitWrite`. The `DiffView` component is wrapped in `React.memo` so commit-textarea typing doesn't re-render every open diff.

### Embedded terminal

A real PTY shell per session, for interactive work the `!`/`!!` exec mode cannot do (it spawns `shell -c` with stdin ignored and no TTY, so ssh/sudo passwords, REPLs, and full-screen programs hang). The design ports DSH's user-terminal model onto the existing per-panel overlay architecture; the full decision record is `.agents/notes/implemented/feature/2026-11-21-embedded-terminal.md` and `docs/superpowers/specs/2026-11-21-embedded-terminal-design.md`.

**Server service.** `server/terminal.ts` (`TerminalSession`) owns one shell slot: node-pty `spawn` of the interactive shell (mirrors `exec.ts` resolution — `ComSpec`/`cmd.exe` on win32, `SHELL`/`/bin/sh` with `-i` on posix, `-NoLogo` for PowerShell), a server-side headless xterm (`@xterm/headless` + `@xterm/addon-serialize`, scrollback `TERMINAL_SCROLLBACK = 1000`), and the `idle → running → exited(exitCode)` state machine. `SessionManager` keeps slots in a `terminals` map keyed by session id — deliberately NOT on the live `Session`, so terminal ops serve DORMANT sessions without spawning a Query; the slot is materialized lazily on first use (`terminalSlot`) and every public op is capability-gated. **Screen == seq invariant:** every output chunk is parsed into the headless terminal synchronously (`term.input('')` marks the write user-input-priority so xterm parses it inline) before its seq is emitted, so `snapshot()` (a synchronous serialize) always reflects exactly the chunks counted by `seq` — this is what makes attach/resync lossless. Persistence is LAZY: the output path only marks the store dirty with a producer closure; the O(scrollback) serialize runs when the debounce fires or `flush()`/`snapshot()` is called, never per chunk (measured: ~4 ms/serialize at 120×30, ~41 ms at 500×200 — under sustained flood a per-chunk serialize is computed and discarded every time and stalled the event loop ~600 ms; lazy production keeps the loop at baseline). The xterm family (`@xterm/headless`, `@xterm/xterm`, `@xterm/addon-serialize`, `@xterm/addon-fit`) is exact-pinned — the invariant depends on headless/serialize internals and the browser xterm must parse chunks identically. Output is ephemeral: it never enters the history ring or the message channel.

**Capability + packaging.** node-pty is an exact-pin `optionalDependencies` entry; `server/terminal-capability.ts` probes it once (lazy `createRequire`, cached, failure logged) and the result rides `SessionInfo.terminalSupported` (host property, not provider — same value live or dormant). Unsupported → the client hides the palette action and the Ctrl+` shortcut no-ops with a toast; nothing else changes. `build.mjs` marks `node-pty` external in BOTH bundles (inline bundling breaks the dynamic `.node` require); `desktop/electron-builder.yml` `asarUnpack`s it and sets `npmRebuild: false` — node-pty is the only production module with a `binding.gyp`, so `@electron/rebuild` would otherwise node-gyp-rebuild it from source (fails without a VS toolchain) even though its N-API prebuilds load under Electron unchanged; koffi has no `binding.gyp` and is already skipped, so the flag leaves its prebuild handling untouched. The Windows ConPTY drain fix ships as `patches/node-pty+1.2.0-beta.15.patch` via `patch-package` (a production dep), gated by `scripts/postinstall.mjs`: patch-package runs only when node-pty actually resolves (`createRequire` from the script, so dev and hoisted consumer layouts both work) — a missing optional node-pty (Alpine musl / no toolchain) skips cleanly instead of failing the whole install with `PatchApplicationError`. `files` ships `patches/` AND `scripts/postinstall.mjs` so npx consumers get both.

**Screen persistence + restart.** `server/terminal-store.ts` writes the serialized screen + meta to `<stateDir>/terminal-screens/<id>.json`, debounced `TERMINAL_SCREEN_DEBOUNCE_MS = 2000` after the last chunk. `schedule()` takes a PRODUCER, not a payload: it runs at write time (timer fire or `flush()`), reading the live screen — so a generation replacement must `cancel()` the pending producer before disposing its serializer (`create()` does), and `dispose()` flushes BEFORE `killAndClear()` releases it. Synchronous flush on shell exit and on unload/shutdown. Explicit close and session delete REMOVE the file; unload/shutdown kill the tree but KEEP it (the restart-restore premise). On boot a persisted screen seeds the headless terminal; a remembered tab's `create()` carries that history into the first new generation exactly once, with `TERMINAL_DIVIDER_TEXT` ("server restarted · previous shell ended · output above is history") as the generation's first output chunk. On win32 the divider + history are scrolled into scrollback before ConPTY's startup screen-clear can wipe them. Persisted `exited` restores the exit banner with NO auto-spawn; natural exit never auto-respawns.

**Sleep guard.** A RUNNING terminal joins the idle guard (`phaseOf` returns `working`) and `sleep()` is rejected 409 with a terminal-specific blame — the background-subagent convention, so an ssh session is never silently killed by sleep. An exited terminal does not block sleep. The overlay header's kill button (trash, beside the hide-X) is the UI path that unblocks sleep: it calls `terminal-close`, killing the tree and clearing the screen.

**Wire channel.** Frames ride a dedicated per-session terminal channel (canonical definitions in `shared/ws-protocol.ts`): client→server `terminal-subscribe`/`unsubscribe`/`create`/`input`/`resize`/`resync`/`close`; server→client `terminal-snapshot`/`output`/`state`/`terminal-error`. `frame-bridge.ts` self-holds `terminalSubs` (independent of the message channel's `subs`), seeds the snapshot on subscribe, and releases the subscription entry by identity when the drive loop ends or throws (a dead channel must not latch the duplicate-subscribe guard); a `terminal-create` with no live entry re-opens the channel (the post-dispose revival — sleep/GC ended the pushable, but the creator expects to see the shell it spawned). Terminal control failures ride `terminal-error` — a DISTINCT kind from the prose `error` frame, which the session synchronizer renders as the persistent chat error bar; the synchronizer ignores `terminal-error` and the channel hook shows it as a transient terminal-local notice (5 s). `terminalId` is a fresh uuid per spawn (generation fence — late frames from a dead generation are dropped); input/resize for a non-live generation reject 409, oversize input (>64 KiB) and out-of-bounds resize (>500×200) reject 400. A viewer that detects a seq gap requests ONE `terminal-resync`; there is no raw-output replay (scrollback trimming would split escape sequences). **Lifecycle broadcast:** every terminal transition (spawn/exit/close/dispose) broadcasts a `session-update` carrying `SessionInfo.terminalRunning` (manager-owned slot state, projected for live AND dormant sessions) — lifecycle-only, never per chunk. `disposeTerminal` pushes an idle `terminal-state` frame to attached subscribers BEFORE ending their pushables, so a keep-alive client heals instead of freezing at 'running'.

**Client.** `src/hooks/useTerminalChannel.ts` is the per-session channel filter, subscribed by `Chat` gated on a `terminalEverOpened` latch (panels that never open a terminal carry no terminal WS traffic). Render isolation: live output churn touches only refs + the leaf `subscribeOutput` listener set, never React state — only state/snapshot transitions (and the rare error notice) re-render the host. The screen anchor applies SYNCHRONOUSLY through a second leaf subscription, `subscribeAnchor` (seeded immediately on registration, run inside the snapshot dispatch) — a passive effect keyed on the snapshot prop would race output frames dispatched before its commit and wipe them. An idle `terminal-state` frame synthesizes the cleared anchor (screen '', restored false), so close/dispose clears the body and the restored badge together. input/resize are guarded on a live anchor (idle fit / exited resize send nothing). The restart auto-create lives here: a stored binding (`localStorage` `crw.terminal.binding.<id>`, the last running terminalId) meeting a `restored:true + idle` snapshot sends `terminal-create` once. `TerminalOverlay` (chrome/banners) + `TerminalBody` (the xterm owner) are NESTED lazy chunks so startup loads neither; Chat mounts the overlay once after first open and keeps it mounted (`Overlay keepMounted`, hidden via `.terminal-overlay.hidden`) so xterm never remounts on open/close — it unmounts only on panel-cache eviction. The overlay joins the `useAppOverlays` mutual-exclusion union as `'terminal'`. **Esc focus gate:** `escapeBehavior='custom'` + `escapeRequiresFocus` routes Esc to the PTY (`input('\x1b')`) only while focus is inside the container; an Esc in a sibling panel falls through to the global interrupt instead of being swallowed. Entries: Ctrl+Backquote toggle (`src/app/terminal-shortcut.ts`, platform-fixed `ctrl`, `allowInInput`, true-modal suppression, palette action from the same factory), Command Palette, and a composer button right of Tasks shown ONLY while running — derived from `SessionInfo.terminalRunning` (the lifecycle broadcast), NOT the channel, so it works before first open, after a reload, and in bystander tabs. The overlay header carries the kill button (trash, `channel.close()`) whenever a terminal exists (running / exited / restored history), beside the hide-X. Light-theme ANSI inks are contrast-guarded (`terminal-ansi-contrast.test.ts`): white/brightWhite ≥ 4.5:1 in both themes, every light colour ≥ 3:1.

**Kill + metrics.** Close/delete reuse `killTreeWin32` with the spawn-time birth-time fence (win32) and process-group kill (posix). Metrics: `terminal_spawn_total` / `terminal_output_bytes` counters, `terminal_active` gauge on the GC tick. Browser E2E: `tests/browser/terminal.spec.ts` under `playwright.app.config.ts` (auto-spawn-on-open with no error bar → type → resize → reload-reattach with the pre-open composer indicator → second tab → exit → restart → sleep 409 blame → kill → kill-then-reopen auto-spawn → kill again → sleep 200 → dormant panel → resume → fresh round-trip → exit); it reads the rendered screen from `.xterm-rows` because @xterm/xterm 6's core renderer is the DOM renderer (no production test hook).

### PDF preview

Both cwd PDFs (ResourceModal file preview) and uploaded PDFs (Uploads Manager eye, sent-message chip, composer-draft chip) render in-app through Mozilla pdf.js — never the code branch (mojibake / `NativeFileEncodingError`) or a bare download. The full decision record is `.agents/notes/implemented/feature/2026-11-24-pdf-preview.md` and `docs/superpowers/specs/2026-11-24-pdf-preview-design.md`.

**One lazy chunk, zero startup cost.** `pdfjs-dist@6.3.289` + its worker source (`pdf-assets.ts` `?raw` import) + every support asset (cMaps / standard_fonts / wasm) are base64-inlined into a SINGLE `React.lazy` chunk behind `LazyPdfBody` — the only dynamic import door. `build/pdfjs-assets-plugin.ts` exposes the `virtual:pdfjs-assets` map (read from the installed package, version-locked to the worker, LICENSE_* excluded from data and emitted as an Apache-2.0 banner on the PDF chunk) AND gates startup-zero: `generateBundle` scans every entry's transitive STATIC import closure for pdf.js markers (`startupPdfjsChunks`) and fails the build if any startup chunk carries them. `optimizeDeps` excludes pdfjs-dist. A failed chunk load needs a page reload (React caches rejected lazy imports).

**Worker-owned runtime, no fallback.** `pdf-runtime.ts` `openPdf(bytes, signal, reportFailure)` copies the bytes (`bytes.slice()` — pdf.js transfers the buffer), spawns an explicit Blob module Worker from the inlined source with a `crw-pdf-worker-ready` handshake, bridges it via `PDFWorker.create({port})`, and calls `getDocument({cMapPacked:true, useWorkerFetch:false, useSystemFonts:true, enableXfa:false, stopAtErrors:true})`. `createPdfBinaryDataFactory` answers pdf.js 6 resource requests by exact-name `Object.hasOwn` lookup into the inlined map, returns a fresh `Uint8Array` per call, and throws loudly on an unbundled name — ZERO network/CDN fallback. There is NO fake-worker/main-thread degradation: a worker transport failure is a retryable `PdfWorkerFailure` (`pdf-errors.ts` `classifyPdfFailure` → worker / password / failed). Disposal races `loading.destroy()` against a worker-broken promise so a dead worker cannot hang teardown, then terminates the worker and revokes the Blob URL. The runtime avoids ES2024 APIs (`Promise.withResolvers`/`AbortSignal.any`) — repo lib is ES2022 — using a local deferred + dual abort listeners.

**CJK is core, not an edge.** Embedded fonts render natively; non-embedded CID fonts (e.g. STSong-Light / Adobe-GB1 / GBK-EUC-H) decode through the inlined cMaps and draw glyphs via `useSystemFonts:true` system-font fallback (the user's Chinese Windows ships SimSun/Microsoft YaHei — one step beyond DSH, which ships no CJK TTF). Scanned CJK rides the inlined JBIG2/JPX wasm. Glyph pixels depend on a system CJK font being present (Linux CI needs fonts-noto-cjk); the text-layer decode is font-independent.

**Rendering.** `PdfBody` mounts all `numPages` as `PdfPage` skeletons; only pages near the viewport render (IntersectionObserver rooted at the scroll container, `rootMargin:'100% 0px'`). `renderPdfPage` (`pdf-document.ts`) draws into an OFFSCREEN buffer at `min(devicePixelRatio × zoom, sqrt(2^24/(w·h)))` raster (96/72 viewport) and `drawImage`s to the visible canvas only when complete — double-buffered so a zoom redraw never flashes blank; cancellation barrier + `page.cleanup()` in finally. The selectable overlay is the official `TextLayerBuilder` (`pdf-text.ts`, laid out detached, appended on `onAppend`, ResizeObserver width-fitting) over a hand-copied `pdf_viewer.css` subset in `file-viewer.css` (tracks the pinned version, guarded by `pdf-viewer.test.ts`).

**Zoom + view-state.** `pdf-zoom.ts` + `PdfZoomControls.tsx`: continuous scroll, fit-width default (shrink-only), 25–400% fixed (25% steps, presets 25/50/100/150/200%), Ctrl+wheel / trackpad-pinch anchored at the pointer with scroll compensation (120ms settle), auto-hiding floating controls. Layout resizes SYNCHRONOUSLY via `--pdf-zoom` + `data-pdf-zoom-mode` CSS variables while the bitmap redraws asynchronously at the settled zoom. `pdf-view-state.ts` is an IN-MEMORY module store keyed by the (session,file) resource address (uploads by `upload:<id>`): last page + zoom survive body unmount/remount, forgotten on tab close; page retention arms only after a user scroll.

**Two byte sources, one viewer.** cwd PDFs: the `file` resource provider requests `encoding=base64&maxBytes=PDF_PREVIEW_MAX_BYTES` from the live-only read-file route; `FilePreviewBody`'s PDF branch (gated on `isPdfPath` + base64) decodes once per payload and refuses a truncated read. Uploaded PDFs: `UploadPdfViewer`/`UploadPdfModal` fetch RAW bytes by upload id from `GET /api/uploads/:id/content` (durable, no live session), bypassing the cwd file provider; the chips carry only a `FileAttachmentRef`. `PDF_PREVIEW_MAX_BYTES = 20 MiB` (`shared/read-file.ts`) — over-cap is REFUSED with a hint (the image precedent), never a truncated render; the upload path refuses on the recorded size BEFORE fetching. `shared/uploads.ts` adds a CLIENT-ONLY `'pdf'` preview kind — deliberately NOT an `IMAGE_MIMES` entry, so the served Content-Type stays `application/octet-stream` + nosniff and non-PDF chips keep their download behavior.

**E2E.** `tests/browser/pdf-preview.spec.ts` (app-config fixture harness, a dedicated idle session) drives the REAL `openPdf` end-to-end against real pdf.js — production lazy chunk + Blob worker + inlined assets + TextLayerBuilder — asserting canvas pixels, decoded/selectable text, mouse-clicked zoom presets + gestures + retention (the preset menu portals above the modal on the dedicated `--z-menu` tier), CJK glyphs, a scanned image-only page, all three uploaded surfaces, and over-cap refusal; each test pins zero uncaught page errors and zero PDF-asset network requests. Hand-built fixtures live in `tests/pdf-fixture.ts` (Latin / non-embedded GBK CJK / scanned / oversize — no binary assets); the real-library Node smoke is `tests/pdf-smoke.test.ts` (legacy build, Node worker thread). Known E2E gap: Safari trackpad-pinch (gesturestart/change) is not synthesized by ctrl+wheel — disclosed in the note.

### Build: single-file bundle

`build.mjs` uses esbuild to bundle `server/cli.ts` into `dist/cli.mjs` as ESM for Node 20. `@anthropic-ai/claude-agent-sdk` is marked `external` — it spawns the real `claude` CLI at runtime and bundling it breaks filesystem-relative lookups. ### Logging

`server/log.ts` exports `createLogger(scope)` — a scoped logger with 5 levels (`error` > `warn` > `info` > `debug` > `trace`, default `info`). **All diagnostic logging goes through it; never use bare `console.*` for diagnostics.** Each module declares one logger at top: `const log = createLogger('scope')`. The `[scope]` tag is auto-prepended — don't hand-write `[scope]` prefixes in messages. Session-id context stays in the message body, e.g. `log.info(`[${id}] spawned…`)`.

Configuration: `LOG_LEVEL` / `LOG_SCOPES` env vars at boot, or `PUT /api/log` / `GET /api/log` at runtime (no restart needed). `LOG_SCOPES=ws,session` mutes everything else; `*` matches all. `DEBUG_SESSION=1` is a back-compat alias for `LOG_LEVEL=debug`. File logging (daily-rotated `<stateDir>/logs/server-YYYY-MM-DD.log`, 14-day retention) is opt-in via `config.json` `logToFile: true`; `enableFileLogging(stateDir)` activates it.

**Metrics:** `server/metrics.ts` is an in-process registry (histograms with p50/p95/p99, counters, gauges) feeding `GET /api/metrics`, rendered in SettingsPanel's Performance tab. Instrumentation covers HTTP requests (route-template labels), WS fan-out, pump `next()` cadence, replay build, session spawn→init, interrupt, SDK control round-trips, the event-loop probe windows, permission pending counts, recap/commit API calls, and the image-persistence measurement set: `session_ring_images` / `session_ring_image_base64_bytes` and `session_transcript_images` / `session_transcript_image_base64_bytes` gauges (recorded by the 60s GC tick; the ring is bounded, the transcript seq store is not, so they are separate and never summed), `session_jsonl_bytes` / `session_jsonl_bytes_max` gauges (the provider-owned transcript JSONL, statted on the same tick — the SDK's copy is not shrinkable by attachment references), `user_message_images` / `user_message_image_base64_bytes` (sendContent), `ws_message_images` / `ws_message_image_base64_bytes` (unique live message-frame serializations), and `history_page_images` / `history_page_image_base64_bytes` (`/history` and `/messages`). Every series in that set is defined over base64-carrying blocks, so durable image refs never feed them — ref turns stop growing the counters and retention gauges, which is the intended measurement win, not a semantics change. The Performance tab renders the retention gauges and an Image payloads counter group; large composer drafts (≥1 MB of base64) log `[draft-images]` through `console.debug` (ref drafts carry no base64, so the log stops firing for them). `METRICS=0` disables collection (endpoint returns the empty snapshot). Series labels are finite enums only — never add session ids or uuids as labels. To attribute _which code_ blocks the loop (metrics only quantify it), attach `node-loop-detective <pid>` or run `clinic flame` against `dist/cli.mjs`.

On the server, bare `console.*` is reserved for three cases that must bypass the logger: `log.ts` itself (the implementation), `cli.ts` user-facing output (startup banner, QR codes, listen URL, HELP text, token prompt, shutdown signal, fatal exit), and `errors.ts`'s `onError` fallback (logger may be unavailable). `event-loop-probe.ts` takes a `log` callback so callers inject their own logger. `server/debug.ts` (`debugLog`/`debugWarn`) has been removed — use `createLogger(scope).debug/.warn`. The client's large-draft `[draft-images]` diagnostic in `useDraftImages` is the sole deliberate client-side `console.debug`.

## Conventions worth knowing

- `Options.includePartialMessages` defaults to `true` on session create so clients can render streaming deltas. Callers can override.
- When a session is deleted while permissions are pending, each pending is resolved as `{ behavior: 'deny', message: 'session closed', interrupt: false }` so SDK awaiters don't hang.
- The deny path always returns `interrupt: false` — the model sees the deny result and re-plans instead of aborting the whole turn.
- `SessionManager.send()` and `sendContent()` broadcast the user message to local subscribers and history _in addition to_ pushing it into the SDK input. The manual broadcast gives the UI an instant "I sent" bubble without waiting for the SDK to read the input queue. On the pinned SDK (0.3.311 / CLI 2.1.311, probe-verified — see `.agents/notes/implemented/architecture/2026-11-19-user-frame-origin-identity.md`) host prompt echoes do NOT stream back through the Query stream at all; the CLI's synthetic user frames (compact summaries, `<local-command-stdout>` logs, skill injections) DO, carrying `isSynthetic`/`isReplay` live but not the disk-only `isCompactSummary`/`isMeta` markers. `session-pump.ts` classifies every null-parent user frame by positive origin (`classifyUserFrameOrigin` in `shared/user-frames.ts`): uuid in the send ledger → host echo (dropped, exact-uuid pairing via `onPromptEcho`); synthetic marker → forwarded with server-stamped visibility markers matching disk truth; unmarked foreign uuid → forwarded fail-visible and logged. Synthetic frames never pair onto the ledger and never arm turn state. `turnActive` follows input consumption (`onInputConsumed`, both providers, gated on `shouldQuery !== false`); the pump's `onTurnSettling` passes an explicit `settlesTurn` (an empty result is a background bookend only when it carries no `local_command`). The client's `isCompactSummary` comes from the frame marker alone — no boundary-adjacency heuristic.
- `HttpError(status, message)` thrown from the manager is translated to a JSON response by the `onError` hook in `buildApiRouter`.
- Server-side defaults (model list, recap model, etc.) are loaded from `~/.claude-react-web/config.json`, not env vars — `server/config.ts` reads no `process.env`. The CLI `--model` flag and the in-app settings panel are the override paths. See `CONFIG.md` for the full field reference.
- Context-window size presets (`contextSteps`) have been removed. The context window is now determined by the SDK/model automatically.
- Native context capacity is owned by `NativeProvider`'s exact-route `NativeModelContextResolver` (profile override → current-transport discovery → `nativeDefaultContextWindow` fallback, config default 1M), not a second model table in sessions or the manager. `NativeSession.getContextUsage()` supplies the current model window and threshold; `SessionManager` owns compaction and checks raw pressure before idle native dispatch (explicit `autoCompactWindow` → provider threshold → ratio only when undefined). Threshold `0` means no viable proactive compaction, and `totalTokens > maxTokens` remains valid down-switch pressure; capacity metadata never enters native session logs.
- Native file reads and guarded edits share one per-session `NativeReadState` (a 256-real-target LRU of pending host observations, contiguous model-window candidates, and seeded identities; never transcript history). Model Read returns at most 2000 lines and 1 MiB per window, resuming only exact next-line/byte continuations; host reads retain only complete observations for the manager's mtime+identity seed. Edit requires current complete-read evidence, caps both original and computed replacement at 8 MiB, precomputes UTF-8 expansion before allocation, and keeps target validation, bounded internal read, `truncate(0)`, positioned write, and capped exact readback on one writable `FileHandle` with pre/post identity checks. In-place auto-compact preserves this state; `/clear`, clear-with-seed manual compact, resume, fork, and destroy replace or clear it, so those sessions must reread.
- Publishing: no `publishConfig` in package.json — pass `--registry` on `npm publish` if you want a non-default target.
- QuestionDialog: after the user answers, the dialog lingers for ~3s showing the answer inline (via `initialAnswers` prop), then auto-dismisses. Questions also support an "Other" free-text option.
- `Shift+Tab` cycles through permission modes (default → auto-accept → bypass).
- `api_retry` system messages render as an amber retry pill in the WorkingBubble (wait time + attempt count, e.g. "26s 7/10", to the right of the timer / token-rate chips; the phase label KEEPS its slot, dimmed via `.working-bar-retry`; `waiting` suppresses the pill), never as a transcript row — the transient `mirror.apiRetry` slot is the single source (`toTranscriptItem` returns null for it; the ring copy exists so a reconnecting tab's incremental replay re-arms the slot). Every `system/api_retry` on the host stream is a MAIN-thread retry — verified against the CLI binary: the emitter attaches no `parent_tool_use_id`, and the subagent-stream forwarding loop skips the child's api_retry frames (a subagent's retry rides a `tool_progress` frame with data.type `agent_api_retry`, which the pump drops with every other tool_progress) — so the reducer's slot routing needs no parent check.
- Git: never spawn through a shell — always go through `runGit()` in `server/git.ts`. See the **Git integration** section for the full path-validation and `confirm: true` rules.
- There are THREE sidechain parents, not two: `Agent`/`Task`/`Explore` (→ SubagentCard), `Workflow` (→ WorkflowCard), and a **forked** `Skill`. Most Skill calls only load SKILL.md into the current conversation, but the CLI can also run one as its own agent and return just a report (`Skill "x" completed (forked execution)`); the fork's whole inner conversation then arrives as frames whose `parent_tool_use_id` is the Skill's tool_use id. WS-replay-verified against a live `code-review` call: 64 frames — 13 Bash, 10 Read, 9 nested `Agent` launches — hung off one id. This matters because `buildTranscriptRows` renders root frames only and each sidechain parent must own its children's rendering: before `activeSkills` (`getSkillStarts` → `SkillRecord.childCalls`, reducer branches next to the Workflow ones) that work was dropped with no owner and no entry point, while the nested Agents still got `activeSubagents` records — so their bar entry (per-agent chips at the time; the swarm pill since) appeared with no card behind it, and vanished for good when the records cleared. The Skill card's `forked execution` row is gated on `childCalls.length > 0` so the ordinary context-only call is untouched, and drill-in reuses SubagentOverlay (`parentToolUseIdFilter` = the Skill id, record adapted by `skillRecordAsSubagent`) rather than adding a third overlay.
- CSS: never hardcode color hex values — always use theme CSS variables (e.g. `var(--btn-hover-bg)` not `#242a35`). Every new color must be defined in both `:root` (dark) and `[data-theme="light"]` blocks. This prevents light/dark theme regressions.
- **Understand the problem before you touch anything.** Every change (CSS, logic, API, architecture) must start from a full understanding of the problem. Don't fix something the moment it "looks wrong" — first trace the context, understand the design intent, and locate the root cause, then act. Changing code before you understand it only treats the symptom and risks introducing new problems.
- **Prove root causes with logs before fixing — never guess, never add fallback code.** When debugging a bug, add temporary logging first (server `log.info` / client `console.log`), have the user reproduce it, and read the actual runtime values before claiming a root cause. Do NOT add "fallback / default / workaround" code as a speculative fix before the root cause is proven by data — guessing introduces unrelated changes, wastes round-trips, and masks the real problem. Remove the debug logs once the root cause is confirmed and the fix lands.
- **Don't add defensive code prematurely.** Handle only the states and inputs that can actually occur; write code so real errors surface loudly (throw, reject) instead of silently absorbing them with speculative null-checks, optional-chaining guards, try/catch, or fallbacks for failures never observed. Add a guard only when the failure is proven real (logs / repro) or an API contract demands it — a silent fallback masks bugs and makes the next debugging round harder.
- **Prefer architectural fixes over accumulating conditional branches.** Don't blindly add guards or special-case branches to work around a problem. When a fix starts accumulating edge cases, stop and re-evaluate the state model, ownership boundaries, and data flow; consolidate related behavior into an explicit architecture (single writer, clear lifecycle, unified decision point) instead of patching each new case. Conditional branches introduced to work around a defect must represent real, proven conditions within a coherent state model — not speculative distinctions introduced to hide design defects.
- **Never commit unreviewed code.** Every code change must pass a review (self-review or peer review) before committing. Run the review against the full diff (`git diff HEAD` for uncommitted, or the commit range for a feature branch), verify findings, and fix any confirmed issues before the commit lands on `main`. A commit without a prior review is a process violation, not a shortcut.
- **Auto-trigger `code-review` for unreviewed changes.** Whenever there are uncommitted changes that have not yet been through a code review, run the `code-review` skill on the full diff before declaring the work done or committing — don't wait to be asked. Verify each finding against the code before fixing, and re-run the review on non-trivial fixes since those fixes are themselves unreviewed.

## Agent Notes

`.agents/notes/` holds durable decision records — the _why_, the alternatives that lost, and what a change knowingly gave up — for decisions code, tests, and docs cannot explain. Claude Code does not discover this directory; treat `CLAUDE.md` as the entry point and read notes on demand.

- Path-encoded layout: `.agents/notes/{proposed|implemented|rejected}/{feature|bug-fix|simplification|architecture|process|testing}/yyyy-mm-dd-topic-title.md`. The full contract is in `.agents/notes/README.md`.
- Write or update the owning note in the same change as the decision. Update an existing note rather than duplicating it, and search for superseded notes first; mechanical or local edits are exempt.
- `npm run verify:agent-notes` gates the structure (also part of `npm run verify`). Do not add an index file.

## App Plugins (Mods)

A separate extension system (`shared/app-plugins/`, `server/app-plugins/`, `src/app-plugins/`) lets plugins add menus, commands, settings, and panels to the **app shell** — distinct from the Claude Plugin Marketplace (`mp-store`, which extends the agent) and MCP. Plugins declare a `crw-plugin.json` manifest (commands/contextMenus/actions/configuration); background code runs in a per-plugin Node subprocess over JSON-RPC/stdio; the UI surface is declarative, never raw React/DOM. Trust model: a background plugin is a **trusted local program** (can `import node:fs`); permissions are consent UX + Host API feature flags, NOT a sandbox. The enforced boundaries are the network broker (SSRF: HTTPS-only, host allowlist, pinned-IP lookup), workspace adapter (realpath + `isPathInside`), and a cleaned subprocess env (no authToken).

Install paths: local-directory (`POST /api/app-plugins/install` `{source:{type:'local',path}}`) and **marketplace** (`POST /api/app-plugins/marketplaces` clones a GitHub repo → `app-plugins-marketplace.json` catalog or auto-scan → `POST /marketplaces/:id/plugins/:name/install`). `AppPluginRecord.source` is `local | marketplace` (marketplace provenance for updates/GC). Marketplace refresh `gitPull`s + revalidates installed plugins (permission escalation → `permission-required`).

**Update surface — deliberately shared with the Claude Plugin Marketplace.** Both settings panels expose the same row control (`MarketplaceUpdateButton`) and the same status-line wording, so one word — `Update` — means one thing in both: _sync this marketplace from upstream_. What that sync clears differs per subsystem and is inherent: the Claude panel's plugins are read live out of the clone, so the pull IS the update, while an App Plugin is an installed copy, so the App row pull refreshes the catalog and the per-plugin `Install`/`Update`/`Installed` buttons apply it (selective update needs that two-step, which is why the row button is pull-only). `POST /api/app-plugins/marketplaces/check-updates` is the App-side twin of the Claude panel's `check-updates` (non-mutating `git ls-remote` vs `lastSha`, per-marketplace errors isolated, `local` records excluded) and drives the row's warn state. The App panel's `Update all` stays available when nothing is badged — unlike Claude's — because its job also includes reconciling installed copies that lag the catalog with the repo already at HEAD. The `local` (bundled) marketplace has no upstream, so it renders no Update control at all; `seedBuiltinMarketplace` **re-parses** the bundled dir on every boot instead, since an app upgrade adds plugins to that directory while the persisted manifest still describes the previous release.

**`plugins/` directory** is the source of truth for official first-party plugins + the marketplace catalog (`app-plugins-marketplace.json`). It is published as a **separate lightweight GitHub repo** for distribution (users add its URL in the UI); `"files": ["dist"]` keeps it out of the host npm package. To publish/sync: `git subtree split --prefix=plugins -b marketplace-main && git push <marketplace-remote> marketplace-main:main`. The `translator` plugin (select text → right-click → LLM translate → popover) is the first. `fixtures/app-plugins/` holds framework-verification fixtures (not distributed). `plugins/` and `fixtures/` are eslint-ignored; `plugins/**/*.test.ts` runs under vitest.
