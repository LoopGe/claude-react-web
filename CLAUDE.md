# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A local browser UI for `@anthropic-ai/claude-agent-sdk`. Ships as a single `npx claude-react-web` binary that serves both the Hono API (port 3456) and the built React client. Sessions are backed by a pluggable **provider** layer (`server/providers/`); the default `claude` provider wraps a live SDK `Query` per session, so multi-turn conversations, interrupts, model switches, and permission-mode changes all drive an actual subprocess.

## Commands

```bash
npm install
npm run dev         # concurrently: tsx watch (server :3456) + vite (:5174, /api proxied)
npm run build       # build:client (vite → dist/client) then build:server (esbuild → dist/cli.mjs)
npm run typecheck   # tsc -p tsconfig.json + tsc -p tsconfig.node.json (both --noEmit)
npm run test        # vitest run (server unit tests + client hook tests)
npm run lint        # eslint .
npm run start       # run the built dist/cli.mjs directly
npm run preview     # build + start
```

Launch env: Anthropic credentials live in `~/.claude-react-web/config.json` (`authToken` / `baseUrl`), not env vars — `server/config.ts` reads no `process.env`; the server injects them into each SDK subprocess. The CLI warns at startup if `authToken` is unset. CLI flags: `-p/--port`, `--host`, `--token` (web access token; auto-generated on non-loopback host), `-o/--open` / `--no-open`, `--cwd`, `--model`, `--state-dir`, `--claude-binary`.

Two tsconfigs exist because the browser (`src/`) and Node (`server/`, `build.mjs`, `vite.config.ts`) have different `lib`/`types` needs; always run both when typechecking. Server tests run in Node; client hook tests run with jsdom via `environmentMatchGlobs` in `vitest.config.ts` (plus per-file `@vitest-environment` docblocks). `setupFiles` points at `src/test-setup.ts`, which registers `afterEach(cleanup)` — `globals: false` means @testing-library/react's own auto-cleanup never self-registers, so without it every `render()` stays mounted past its test and an unmount-cancelled timer can fire inside vitest's jsdom teardown (`ReferenceError: window is not defined`, exit 1 with all assertions green). Don't re-add per-file `afterEach(cleanup)`.

## Architecture

### Server: one provider session per tab

`server/session-manager.ts` is the core. It owns a pool of sessions, each backed by a **provider session handle** (`server/providers/types.ts` — `ProviderSessionHandle`) rather than an SDK `Query` directly. The default `claude` provider (`server/providers/claude/claude-provider.ts` + `claude-session.ts`) is the one that wraps the SDK `Query`; providers are registered in a `ProviderRegistry` (`server/providers/registry.ts`) and selected per session, so the manager itself is provider-agnostic. The `claude` provider advertises a `capabilities` set (supports interrupt / model switch / MCP / resume / fork / plugins / fast mode / effort level / …) that the manager guards control operations against.

For each session the manager holds:

- A provider handle exposing a queued input (`enqueueUserMessage` / `sendControlMessage` / `clearQueuedInput`) and a streamed `messages` async iterable. Under the hood the `claude` provider backs this with a `Pushable<SDKUserMessage>` queue (`server/pushable.ts`) whose `.iterable` is passed as `prompt` to `query({ prompt, options })`. User turns from HTTP `POST /sessions/:id/messages` are enqueued — via `send(id, text)` for plain text or `sendContent(id, content)` for multimodal (text + image) arrays.
- The provider's message stream. A background `pump()` task (`server/session-pump.ts`) iterates it, appends every message to a bounded history ring (`HISTORY_CAP = 500`), and fans out to all live WebSocket subscribers of that session. Ephemeral event streams bypass the ring entirely via early-`continue` (`prompt_suggestion`, and the `task_started`/`task_updated`/`task_progress` task-state stream — see `tasks-snapshot` in the frame list below). `system/thinking_tokens` is likewise ring-bypassed but still forwarded live (a transient thinking-token estimate the client mirrors into the WorkingBubble); `tool_progress` frames are dropped outright. Durable system frames outside the default allowlist must be added to `BROADCAST_SYSTEM_SUBTYPES` (`server/history-utils.ts`) — adding one there also makes it renderable from disk pages (history-reader's `isRenderable` reuses the set) and requires top-level payload passthrough in history-reader's `normalize()` plus a client unhide in `shouldHideByDefault` + a MessageList render branch. Currently allowlisted beyond the basics: `permission_denied` (non-interactive tool denial card), `informational` (loop text banners), `model_refusal_fallback` (refusal-fallback notice; its `retracted_message_uuids` — and assistant `supersedes` — drive eviction of the refused leg inside the client reducer's `applyMessage`, reusing the `EVICT_MESSAGES` machinery, so live replay and disk replay both evict), `local_command_output`, `memory_recall`, `elicitation_complete`, `api_retry` (rate-limit retry indicator — durable in the ring only so a reconnecting tab's incremental replay re-arms the client's transient slot), `task_notification`.
- A `pending` map of tool-permission requests (`PendingPermission`). The session registers a `canUseTool` callback (unless `permissionMode === 'bypassPermissions'`) that parks each request in this map, broadcasts on the permission channel, and resolves the SDK's promise only when the client POSTs a decision. The broker lives in `server/permission-broker.ts`.
- Two subscriber sets: one for messages, one for permission events. Each WebSocket connection gets its own queue+waiter iterable so a slow client can't block the pump.

Control operations (`interrupt`, `setModel`, `setPermissionMode`, `applyFlagSettings`) are delegated through the provider handle (guarded by its capabilities); the `claude` provider forwards them to `Query`'s methods, which implement them as in-band control requests to the CLI subprocess. The session holder also proxies `supportedModels`, `supportedCommands`, `supportedAgents`, `mcpServerStatus`, `getContextUsage` (again, capability-gated).

Stuck-session GC runs every 60s via `server/session-health.ts`. **Idle sessions are no longer auto-unloaded** — they persist until explicitly deleted by the user. The GC tick only catches sessions that are mid-turn (`pendingTurns > 0` or permissions pending) and have been silent longer than `workingStuckMs`: it auto-interrupts first, then escalates to a force-unload if the subprocess stays wedged (see `checkStuck`'s three cases: mid-turn silence, init-never-landed, and already-interrupted-escalation).

### WebSocket + REST wire protocol

The server uses a single WebSocket connection per browser tab (`server/ws.ts`) that multiplexes all channels. The canonical frame definitions live in `shared/ws-protocol.ts` (generic); `server/ws-protocol.ts` and `src/ws-types.ts` are thin instantiation aliases that bind those generics to the server's SDK types and the browser's lightweight types respectively — **not** duplicated mirrors. The client connects via `useWsHub` (`src/hooks/useWsHub.ts`) which provides exponential backoff, ping heartbeat, and ref-counted subscriptions.

**WebSocket frame kinds** (server → client) — canonical list in `shared/ws-protocol.ts`:
- `sessions-snapshot` / `session-created` / `session-update` / `session-removed` — global session list mutations
- `replay` / `replay-done` / `message` — per-session message stream (replay on subscribe, then live)
- `subscribe-result` — the server's answer to one `subscribe` frame: `{ ok, reason: 'served' | 'already-live' | 'starting' | 'refused' | 'closed' }`, the STATE of this connection's per-session channel (the prose `error` frame keeps the message). Exactly one per accepted subscribe, so the client never infers channel liveness from ambient frames. `already-live` also RE-SERVES the replay (a listener may have attached after the first one); a `closed` result is emitted when a channel ends (unload / sleep / terminate), which is the only per-connection signal for that
- `message-consumed` — the SDK has read a queued user turn (drives the "sending → sent" transition). The live frame only serves already-attached tabs; the durable half is `consumedAt` on the ring entry itself, which `dispatchUserMessage` (idle direct hand-off, stamped before the broadcast) and `onInputConsumed` (queue-shift, stamped by a tail scan of `history`) keep in sync. Both are required: a ring entry with `receivedAt` but no `consumedAt` replays as permanently 'queued' on any client without a cached transcript
- `messages-withdrawn` — queued user turns were withdrawn by an interrupt with `cancelQueued` (host input-queue drain + SDK `interrupt_cancel_queued_v1`); the server removed them from its replay ring and live tabs evict the matching bubbles via the `EVICT_MESSAGES` reducer action. The withdrawal set is restricted to still-unpaired `promptUuids` entries, so control messages riding the input queue (compact hand-off seed), CLI-internal uuids, and already-echoed prompts are never evicted, and the matching unpaired sidecar entries are pruned so `onPromptEcho`'s FIFO pairing (and thus `rewindFiles` mapping) stays aligned. The session remembers a capped withdrawal window (`withdrawnUuids`) and seeds every NEW msgstat subscriber with one synthetic frame — a tab disconnected during the stop heals on reconnect, since incremental sinceUuid replay can never re-send ring-removed messages. Rides the same per-session input-queue-status channel as `message-consumed`
- `permission-request` / `permission-resolved` — per-session tool permission events
- `elicitation-request` / `elicitation-resolved` — per-session MCP elicitation (OAuth) events
- `dialog-request` / `dialog-resolved` — per-session user dialogs (`Options.onUserDialog`, currently `refusal_fallback_prompt`). The resolved frame carries `retractedMessageUuids`; every tab evicts those messages from its transcript store via the `EVICT_MESSAGES` reducer action on receipt
- `session-cleared` — a `/clear` completed and the server truncated its history ring; clients reset their transcript store
- `global-permission-request` — cross-session permission notification (for sidebar badge)
- `cli-notification` — a CLI notification frame (SDK `system/notification`: "waiting for your input", idle nudges) narrowed by the pump (`cliNotificationOf`, early-continue — never the ring or message channel) and mirrored onto the global channel so App-level code fires a browser/OS notification even when the session's panel isn't mounted. Client-side it routes through `useSessionNotifications.maybeCliNotify` (same three-state skip/toast/desktop dispatch as permissions, but transient: CLI-suggested timeout clamped to 2–30s, low/medium priority silent on desktop, `key`-tagged dedup)
- `context-usage` — per-session context window usage
- `prompt-suggestion` — predicted next-user-prompt pushed after each turn when the SDK's `promptSuggestions` option is on (default). Ephemeral: it bypasses the history ring entirely (pump early-`continue`s on `prompt_suggestion` messages), rides a dedicated psug channel mirroring context-usage, and is cleared client-side when the user sends a message or the transcript is cleared
- `tasks-snapshot` — full background-task list snapshot (server-side `session.tasks: Map<taskId, TaskRecordUi>`, `shared/tasks.ts`). The pump folds SDK `task_*` system frames via `applyTaskEvent` (`session-pump.ts`, unit-tested): `task_started`/`task_updated`/`task_progress` are ephemeral (early-`continue`, never ring, never the message channel) and only ride this dedicated channel; `task_notification` ALSO folds state but keeps the ring+broadcast path (the client reducer's async-subagent completion branch matches on it) and cancels the matching subagent watcher via the `onTaskNotification` pump dep. The watcher itself seeds a `TaskRecordUi` (taskId = agentId) for background Agent dispatches the CLI sends no frames for, and its synthesized notification folds the seed to terminal. Terminal records are capped at 50 (oldest evicted). The client's `TASKS_SNAPSHOT` reducer action also enriches matching `activeSubagents` (taskId/progressSummary join by toolUseId; `isBackgrounded` flips 'running' → 'background'). `TASKS_SNAPSHOT` is the SINGLE authority for a subagent's `isAsync` (async/sync badge truth): it writes `task.isBackgrounded` for both true and false, on live and terminal records. `task_notification` is a pure completion signal for ALL subagent tasks (async and foreground — the CLI emits one for foreground agents too), so it never stamps `isAsync`; launch-ack tool_results are skipped by a pure-regex guard (never settled as results), and a `running` record is only deferred to `pending` at turn end when `mirror.tasks` still lists a live backgrounded task
- `session-recap-update` — a recap state transition (pending / ready / error / cleared) for this session
- `hook-run` — a hook lifecycle event fired during the turn
- `commands-changed` — the supported slash-command set changed (e.g. after dynamic skill/command discovery)
- `git-snapshot` — work-tree git status snapshot (status / branches / stashes inline), computed once per repoGroup (`gitGroupKeyOf`: `repoRoot ?? cwd`) after any filesystem-mutating event and fanned out to all sessions in the same group; new subscribers are seeded with the most recent frame. Client hooks `useGitStatus` / `useGitBranches` / `useGitStashes` are pure sinks (mount HTTP fetch once + manual refresh preserved; frame arrival replaces state directly, zero refetch). diff / log remain on-demand fetch

`server/routes/index.ts` (`buildApiRouter`) composes the REST surface under `/api` from per-concern sub-routers in `server/routes/` (`sessions.ts`, `permissions.ts`, `uploads.ts`, `recap.ts`, `config-routes.ts`, `health-routes.ts`, `mp-marketplace.ts`, `git-write.ts`, `update-routes.ts`, `search.ts`, `skills.ts`, `hooks.ts`, `dialog.ts`):

- `GET /sessions`, `POST /sessions`, `DELETE /sessions/:id`
- `POST /sessions/:id/messages` — accepts either legacy `{ text }` string or `{ content }` array (text + image blocks for multimodal input). Image blocks use `{ type: 'image', source: { type: 'base64', data, media_type } }`. Total base64 payload capped at 28 MB. Valid image types: jpeg, png, gif, webp.
- `POST /sessions/:id/interrupt`, `/model`, `/permission-mode`, `/settings`
- `POST /sessions/:id/thinking` — set extended-thinking config (`{type:'adaptive'} | {type:'disabled'} | {type:'enabled', budgetTokens}`). Spawn-time rides SDK `Options.thinking`; the live switch maps to `Query.setMaxThinkingTokens` (adaptive→null, disabled→0, enabled N→N — there is no Settings key for thinking) via the provider handle, capability-gated on `supportsThinkingControl`. Bare `{type:'enabled'}` is accepted at create but rejected 400 live (not expressible as a token count). Persisted on `SessionMeta.thinking`, so resume/fork/clear/respawn re-apply it at spawn; `thinkingSupported` (keyword-classified in `effort-capability.ts`) hides the client chip on non-thinking models.
- `POST /sessions/:id/tasks/background` — background in-flight foreground tasks (CLI Ctrl+B semantics; optional body `{ toolUseId }`); `POST /sessions/:id/tasks/:taskId/stop` — stop a running background task. Both delegate through the provider handle, capability-gated on `supportsTaskControl`. `agentProgressSummaries` defaults to on in the claude provider (feeds `task_progress.summary`)
- `GET /sessions/:id/context-usage` `/models` `/commands` `/agents` `/mcp-status`
- `GET /sessions/:id/usage` — structured `/usage` data (session cost/token totals + claude.ai plan rate-limit windows); `GET /sessions/:id/account` — authenticated-account info (email / org / subscription / auth backend, SDK `accountInfo`, narrowed via `shared/account-info.ts`, capability-gated on `supportsAccountInfo`). Both live-Query-only control reads; the client pulls them together in `useSessionUsage` and renders them in the SettingsPanel Usage tab (`UsagePanel`).
- `POST /sessions/:id/rewind-files` — restore files to their state at a user message via the host-managed shadow-repo snapshot sidecar (replaces the former SDK `Query.rewindFiles` path; no live Query required). Body `{ messageId, dryRun? }`: `messageId` is the app-level user-message uuid. `dryRun: true` previews the diff without touching files. Works offline — dormant and terminated sessions can rewind; only real (non-dry) rewinds are blocked while the session is `working` (409; dry-run is still allowed). Restores tracked files to the snapshot state and deletes files that were created after the message. A real (non-dry) rewind fires `git-snapshot`. Result narrowed via `shared/rewind.ts`. Requires a git-based cwd (non-git sessions are unavailable). Client entry: right-click a user message → "Rewind files to this message" → ConfirmDialog showing the dry-run diff. Conversation truncation is the separate discard feature; the two compose.
- `GET /sessions/:id/file-snapshots` — snapshot sidecar capability: whether snapshots are available for this session (`available: boolean`, `reason?: 'disabled' | 'no-snapshot' | 'not-git'`) plus the list of rewindable anchors (`anchors: Array<{ messageId }>`). Does not require a live Query — reads the sidecar directly. 404 for unknown sessions.
- `GET /sessions/:id/history?before=&beforeUuid=&limit=` — disk-paged history (lazy-load older messages, offset semantics: `before` = previous response's `startIndex`, `beforeUuid` = first-page anchor on a disk-stable uuid). Served through the JSONL parse cache (`server/jsonl-cache.ts`): freshness keyed on `(size, mtimeMs)`, appends parse incrementally, entries LRU-capped at 4 sessions (`history_cache_hit` / `history_cache_miss_full` / `history_cache_miss_incremental` metrics).
- `GET /sessions/:id/snapshot-diff?from=<messageId>` — structured diff from a recorded snapshot anchor to the current worktree capture. Returns `{ diffs: Array<{ file, status, additions, deletions, patch? }> }`. Requires the snapshot sidecar to be available; 400 when the anchor is missing or snapshots are disabled. Does not require a live Query.
- MCP on a live session: `POST /sessions/:id/mcp/servers` adds/removes dynamic MCP servers (SDK `setMcpServers`). It accepts the **same two inputs as `POST /sessions`**: `enabledMcpServers` (string[] of global server names resolved from `McpConfigStore`) and/or `servers` (inline `McpServerConfig` map, which wins on name collision). Both are run through `SessionManager.mergeMcpServers` before reaching the SDK, so the dynamic path can reference globals by name. `setMcpServers` has **replace** semantics over the dynamic set, so the merged map must list every dynamic server that should stay connected; an empty result clears them all. `enabledMcpServers` must be a `string[]` (validated on both routes — a stray string is a 400, not iterated char-by-char). Per-server control: `POST /sessions/:id/mcp/:name/reconnect`, `POST /sessions/:id/mcp/:name/toggle`.
- `POST /sessions/:id/permissions/:pid/decide` — `{ behavior: 'allow' | 'deny', persistForSession?, message? }`. Allow paths always echo the original `input` as `updatedInput` (the SDK's runtime Zod schema requires it even though the TS type marks it optional). `persistForSession: true` rewrites every SDK-provided suggestion to `destination: 'session'` so the allowance is Query-scoped, not user-settings-scoped.
- `POST /sessions/:id/fork` — duplicate a session (resumes from the fork point)
- Scheduled sends (server-side, in-memory — NOT persisted across restarts): `POST /sessions/:id/schedules` `{ fireAt, text | content }`, `GET /sessions/:id/schedules`, `DELETE /sessions/:id/schedules/:scheduleId`. A ~1s ticker fires due sends through the same `sm.send`/`sm.sendContent` path as `POST /messages`; body validation is the shared `server/send-body.ts` helper used by both routes. A session reaching fire time terminated/dormant/deleted is marked `failed` (never auto-resumed). Session deletion (observed via the global `removed` feed) drops that session's schedules. Client UI: a clock button beside Send opens a time picker; pending sends render as countdown chips above the composer (`src/hooks/useScheduledSends.ts` poll-reconciles; no WS frames).
- `GET /sessions/:id/dialogs` and `POST /sessions/:id/dialogs/:did/decide` — pending user dialogs (`Options.onUserDialog` / `supportedDialogKinds` pipeline, mirrored on elicitation). `supportedDialogKinds` is hardcoded to `['refusal_fallback_prompt']` (see `shared/user-dialog.ts`); unknown kinds are short-circuited to `{behavior:'cancelled'}` server-side. Decide body: `{ behavior: 'completed', result }` (result ∈ `retry_fallback | edit_prompt | cancelled` for the refusal-fallback kind) or `{ behavior: 'cancelled' }`. The `onUserDialog` + `supportedDialogKinds` pair must always travel together (spawn, resume, respawn) — non-empty kinds without a callback make the SDK spawn throw.
- `POST /sessions/:id/recap` — AI-generated session summary
- `/api/fs` (from `server/fs-routes.ts`) — minimal directory-only browser used by the cwd picker. Lists sub-directories of an absolute path; never returns file contents.
- `/api/git/*` (from `server/git-routes.ts`) — read-only `GET /status`, `/diff`, `/log`, all `?cwd=…`-scoped. Returns `{ isRepo: false }` (200) when the cwd is reachable but isn't a work tree. Writes live under `/api/sessions/:id/git/*` (in `server/routes/git-write.ts`): `stage`, `unstage`, `discard`, `commit`, `abort-merge`, `abort-rebase`, `stash`/`stash-pop`/`stash-drop`, `branch`, `checkout`, `session-files`, `session-diff`, `commit-message`. Destructive verbs require `confirm: true` in the body. After every write the route broadcasts a `git-snapshot` and returns the freshly-fetched `GitStatus` (and `branches` / `stashes` when relevant) so clients update without a second round-trip.
- Disk-backed stores, each mounted as its own router and persisted under the state dir: `/api/mcp-config/*` (global MCP server config, `mcp-config.ts`), `/api/mp/*` (homegrown git-repo marketplace — `mp-store.ts`; enabled entries are injected into `Options.plugins` on spawn, so it's the plugin path), `/api/snippets` (composer text macros, `snippet-store.ts`), `/api/ui-state` (session groups + sidebar order, `ui-state-store.ts`). `/api/update-info` (stateless in-app upgrade check, `update-routes.ts`); `/api/search` (message search across a session); `/api/sessions/:id/skills` and `/api/sessions/:id/hooks` (skill policy + hook config per session, backed by `shared/skills.ts` / `shared/hooks.ts`).

`server/app.ts` composes the Hono app: a web-access auth gate (no-op unless bound non-loopback or a token is set), CORS (reflects trusted/loopback/LAN origins only), a 32 MB body limit, security headers, request logging, then the API/WS routers and static client serving. It also mounts the per-store routers (`/api/mcp-config`, `/api/snippets`, `/api/ui-state`) only when their stores were provided, and locates the built client by walking a few candidate paths so both `tsx server/cli.ts` and the bundled `dist/cli.mjs` find `dist/client/` without config.

### Client: React 19 + Vite

`src/App.tsx` is a multi-panel layout: `SessionList` (left sidebar) and up to 3 `Chat` panels (center). `SettingsPanel` is rendered as a per-panel overlay inside each `Chat` column (absolutely positioned, not a right drawer). A gear button in each panel header opens the overlay; clicking the backdrop or pressing Escape dismisses it. The two most common settings (model, permission mode) also have inline "chip" controls in the panel header that bypass the overlay entirely. A `CommandPalette` (Mod+K) provides fuzzy search across shortcuts and sessions.

Panels leaving the open view do NOT unmount: App keeps an LRU keep-alive cache (`src/utils/panel-cache.ts`, cap `maxOpen + PANEL_CACHE_EXTRA`) and renders those panels `display:none` in the same grid container (`.panel-slot-cached`; CSS Grid skips them in auto-placement, keys never change), so scroll position, follow state, the Virtuoso window and WS subscriptions survive a session switch. Explicit dismissals (X-close, group close, the /clear-fork-discard swap, server-side removal) evict from the cache and truly unmount; LRU overflow evicts silently at the cap. Two protections make the switch lossless: `useTranscriptScroll` treats `clientHeight === 0` as "hidden" and stands down (the browser preserves `scrollTop` across a plain display toggle), and App keeps a persistent scroll memory (`panelScrollMemoryRef`) — snapshotted render-phase (BEFORE the commit reorders/moves keyed PanelSlots, which drops a moved scroller's offset in Chromium) and restored in a layout effect for visible panels. The closing-ghost and `snapshotPanelScrolls` only ever touch visible panels.

- `src/hooks/useWsHub.ts` — single WebSocket connection per tab with exponential backoff, ping heartbeat, and ref-counted subscriptions. All real-time data (session list, messages, permissions, context usage) flows through this hub.
- `src/hooks/useChatStream.ts` — per-session channel filter over the hub, replay buffering. The store mirrors `activePhase` (thinking / writing / tool_use) parsed from `content_block_start` stream events so the UI can show fine-grained progress instead of a generic "Working" label. Also tracks `permissionDecisions` (toolUseId → allow/deny) from `permission-resolved` frames so plan cards flip from pending to approved/rejected even when the SDK doesn't emit a `tool_result` (e.g. `ExitPlanMode`).
- Live-turn telemetry is subscribed at the LEAVES, never by `useChatStream`: every field that hook subscribes to re-renders its host (the whole `Chat` body, or `ChatPanel` for the side chat). `streamingContent` (one change per 80 ms `LIVE_TURN_FLUSH`) is read by `OverlayStreamingRegion` (`message-list/OverlayStreamingRegion.tsx`, the overlay bubble + its exit fade inside `.chat-bottom-stack`) — `MessageList` subscribes only in the `'inline'` render mode, where the text is a Virtuoso data row. `tokenRate` / `activePhase` / `thinkingTokens` are read by `LiveWorkingBubble` (`message-list/WorkingBubble.tsx`; `dwellPhase` + `showThinkingTokens` for the main panel, neither for the side drawer), which also freezes them while AnimatePresence plays its exit (`useIsPresent`), matching the frozen props of the old prop-fed bubble. `ChatStream` exposes only `hasActivePhase` (a boolean selector, `useSessionSelector`) for `computeTurnActive`. Scroll-follow never depended on those parent renders: the bottom stack's ResizeObserver publishes `bottomStackHeight` from the DOM. `streaming-render-isolation.test.tsx` pins Chat and MessageList at 0 renders across a window of flushes.
- `src/hooks/usePastedImages.ts` — manages clipboard-pasted images. Converts `File` objects to base64 `PastedImage` entries with preview URLs. Images are sent inline with the next message as multimodal `content` blocks (text + image) via `POST /sessions/:id/messages`.
- `src/session-store/normalize.ts` — `getSubagentStarts()` scans for Agent / Task / Explore tool_use calls with no matching tool_result. Feeds `WorkingBubble`'s in-flight subagent display: a single `SubagentSwarmPill` (`src/components/message-list/SubagentSwarm.tsx`) at EVERY fan-out width — a lone subagent included — whose popover carries the per-agent detail (`progressSummary` / `lastToolName` / elapsed) and drills into `SubagentOverlay`. Rendering the pill unconditionally is what keeps the bar's height constant, so `.working-bar` carries no `max-height` — the old 120px clip silently ate the tail of a wide fan-out, starting with the "+N more" badge that rendered last. (Before this, ≤2 subagents rendered as individual chips and only wider fan-outs aggregated; a peak-width state machine chose between the two.)
- `ServerMirror.activeWorktree` (`src/session-store/types.ts`) is the session's EnterWorktree/ExitWorktree state, maintained by the reducer so `useSessionActiveWorktree` (the ChatPanel worktree chip) is an O(1) read on every store emit instead of a transcript scan per stream_event delta. Invariant: it always equals `getActiveWorktree(mirror.messages)` — that full-scan fold stays in `normalize.ts` as the reference. The single append site (`updateTranscriptMirror`) folds just the new message (`foldActiveWorktree`); every other path that rewrites `messages` (prepend / loadOlder, `trimFront`, `evictMessages`, `repairChronology`, `replaceStaleCachedMessages`, a worktree-touching `MESSAGE_CONSUMED` / `MESSAGE_STEERED` swap) rescans with `recomputeActiveWorktree`; every mirror reset starts from `createInitialServerMirror` (null). A new code path that writes `mirror.messages` must do the same — `active-worktree.test.ts` drives random action sequences (the seq-window `WINDOW_*` actions included) and asserts the invariant after every step.
- `src/hooks/usePermissionChannel.ts` — permission state, optimistic decide+answer.
- `src/hooks/useApi.ts` — thin `fetch` wrapper with `/api` base (REST calls only; streaming goes through WS).
- `src/hooks/useKeyboardShortcuts.ts` — global shortcut dispatcher with input-safe routing.
- `src/utils/lowlight-instance.ts` — the one lowlight instance (Markdown fences + diff lines). Its 24 highlight.js grammars are deliberately EAGER: all register at import, in the modulepreloaded markdown-vendor chunk, so every code block is highlighted on its first paint. Loading the 16 non-core grammars on demand was built and measured (markdown-vendor 543.5 → 491.6 kB): on a cold first open, blocks in those languages painted uncolored until their chunk landed (113–204 ms, ~1 s under server load), and it was reverted; bringing it back would be a product decision. A new language needs its import AND any aliases so `detectLanguage()` results land in the right grammar. Diff lines also need its name and aliases in the hand-maintained `REGISTERED` set (`isRegisteredLanguage`, the gate in `highlightLineHast`) and its file extensions in `EXT_TO_LANG` (`src/utils/file-display.ts`, the table `detectLanguage()` reads); fences need neither, they resolve through `lowlight.registered`. `lowlight-instance.test.ts` pins the registered set, `REGISTERED`, tag resolution and output against `src/test-utils/markdown-reference.ts`, so update both together; no test ties `EXT_TO_LANG` to the instance.
- `src/types.ts` — UI-side types. The browser bundle does **not** import `@anthropic-ai/claude-agent-sdk`; SDK messages are typed as `SdkMessage` (loose shape with `type/subtype/message/event/...`) and rendered defensively. `src/ws-types.ts` binds the generic frames from `shared/ws-protocol.ts` to browser types (see the wire-protocol note above). Shared, SDK-agnostic types and logic that both server and client use live in `shared/` (`ws-protocol.ts`, `hooks.ts`, `skills.ts`, `mcp-types.ts`, `permission-request.ts`, `session-info.ts`, `search/`, …).
- KaTeX (remark-math, rehype-katex, `katex.min.css` imported first in `main.tsx`) is deliberately EAGER. Lazy-loading it was built and measured: the first open of a session with math on screen showed raw TeX for 250–430 ms and then re-pinned the bottom-following transcript by ~15 px when the rows grew; holding the transcript's first paint until the chunk lands would be a product decision.
- `EasterEggGame` is `React.lazy`. `MessageList` prefetches its chunk while the default empty state is on screen, and the lazy factory returns a synchronously-resolving thenable once the module is cached: React 19 holds a freshly shown Suspense fallback ~300 ms even when the chunk is already there.

Vite dev server on 5174 proxies `/api` to 3456. Production: `vite build` → `dist/client/`, served statically by the same Hono app that hosts the API. An SPA fallback returns `index.html` for any unmatched GET so client-side routing works.

### Git integration

`server/git.ts` is the single owner of git execution. Every git invocation goes through `runGit(cwd, args, opts)` which uses `child_process.execFile` (never a shell) with a fixed argv; user-supplied paths are validated by `validateRepoRelativePath` (rejects absolute paths and `..` segments) AND prefixed with `--` so a path that happens to look like a ref (e.g. `HEAD`) cannot be reinterpreted. Diff bodies cap at `MAX_DIFF_LINES = 500`; the AI commit-message diff caps at `MAX_AI_DIFF_BYTES` (head+tail trim with an elision marker). `getStatus` probes `isInsideWorkTree` and falls back to `{ isRepo: false }`; `getStatusInRepo` is the variant for callers that already validated repo-ness (write routes use this to avoid a redundant `git rev-parse` spawn per write). Exception: `server/snapshot/shadow-git.ts` and `server/snapshot/snapshot-service.ts` execFile git directly for `--git-dir` shadow-repo operations with their own stdin pathspec helpers; they still never use a shell.

Each session gets a `gitStartSha` anchor when it spawns inside a work tree (`tryCaptureGitHead` — null for unborn HEAD, sessions outside repos, or detached states with no SHA available). It's persisted alongside `SessionMeta` and preserved across resume / fork. Three routes hang off it for the GitPanel "This session" view: `session-files`, `session-diff`, `commit-message` (the AI button). When `gitStartSha` is null those routes return empty payloads / 400 — the UI hides the section.

`server/git-broadcast.ts` debounces `git-snapshot` broadcasts per repoGroup. The pump (`server/session-pump.ts`) detects mutating tool_use blocks (`MUTATING_TOOL_NAMES = {Edit, Write, NotebookEdit, Bash}`) by id, and when the matching tool_result lands it calls `scheduleGitBroadcast`. Debounce timing is keyed by **repoGroup** (`gitGroupKeyOf`: `repoRoot ?? cwd`), so bursts of edits across sessions sharing the same repo collapse into a single status computation. `broadcastGitStatusChanged` pushes a complete `git-snapshot` frame and fans it out to all sessions in the group. User-initiated POST writes pass the already-computed fresh status list as `opts.snapshot` to avoid a redundant git spawn. `cancelGitBroadcast(this, id)` on session unload only clears the timer when the triggering session is the origin and no peer in the same group remains alive; otherwise the origin yields to the surviving peer. `getStatusCached` has been removed — the herd-effect stampede it guarded against is eliminated by the snapshot-push design.

`server/anthropic-api.ts` (`callAnthropicMessages`) is the shared Anthropic Messages caller used by both `recap.ts` and `commit-message.ts` — same auth header shape, version pin, 15s timeout. Each caller does its own post-processing (recap strips JSX fragments; commit-message strips code fences) but the wire layer is one place.

Client-side: `src/components/GitPanel.tsx` is a per-panel overlay (mounted alongside `SettingsPanel` inside `Chat`, dismissed by backdrop / Escape, has higher keyboard priority than Settings). `ChatPanel.tsx` renders an always-visible header chip showing branch + dirty/ahead/behind/conflict at a glance; clicking it opens the panel. Hooks are split: `useGitStatus` (status, with WS auto-refetch + a JSON-string no-op compare so unrelated tool runs don't cascade renders), plus `useGitDiff` / `useGitLog` / `useGitBranches` / `useGitStashes` / `useSessionFiles` (lazy-fetched per accordion). Writes go through `useGitWrite`. The `DiffView` component is wrapped in `React.memo` so commit-textarea typing doesn't re-render every open diff.

### Build: single-file bundle

`build.mjs` uses esbuild to bundle `server/cli.ts` into `dist/cli.mjs` as ESM for Node 20. `@anthropic-ai/claude-agent-sdk` is marked `external` — it spawns the real `claude` CLI at runtime and bundling it breaks filesystem-relative lookups. A `createRequire` banner is injected because some dependencies use `require()`. A shebang and `chmod 755` are added so the file is directly executable as the `bin` entry.

### Logging

`server/log.ts` exports `createLogger(scope)` — a scoped logger with 5 levels (`error` > `warn` > `info` > `debug` > `trace`, default `info`). **All diagnostic logging goes through it; never use bare `console.*` for diagnostics.** Each module declares one logger at top: `const log = createLogger('scope')`. The `[scope]` tag is auto-prepended — don't hand-write `[scope]` prefixes in messages. Session-id context stays in the message body, e.g. `log.info(`[${id}] spawned…`)`.

Configuration: `LOG_LEVEL` / `LOG_SCOPES` env vars at boot, or `PUT /api/log` / `GET /api/log` at runtime (no restart needed). `LOG_SCOPES=ws,session` mutes everything else; `*` matches all. `DEBUG_SESSION=1` is a back-compat alias for `LOG_LEVEL=debug`. File logging (daily-rotated `<stateDir>/logs/server-YYYY-MM-DD.log`, 14-day retention) is opt-in via `config.json` `logToFile: true`; `enableFileLogging(stateDir)` activates it.

**Metrics:** `server/metrics.ts` is an in-process registry (histograms with p50/p95/p99, counters, gauges) feeding `GET /api/metrics`, rendered in SettingsPanel's Performance tab. Instrumentation covers HTTP requests (route-template labels), WS fan-out, pump `next()` cadence, replay build, session spawn→init, interrupt, SDK control round-trips, the event-loop probe windows, permission pending counts, and recap/commit API calls. `METRICS=0` disables collection (endpoint returns the empty snapshot). Series labels are finite enums only — never add session ids or uuids as labels. To attribute *which code* blocks the loop (metrics only quantify it), attach `node-loop-detective <pid>` or run `clinic flame` against `dist/cli.mjs`.

Bare `console.*` is reserved for three cases that must bypass the logger: `log.ts` itself (the implementation), `cli.ts` user-facing output (startup banner, QR codes, listen URL, HELP text, token prompt, shutdown signal, fatal exit), and `errors.ts`'s `onError` fallback (logger may be unavailable). `event-loop-probe.ts` takes a `log` callback so callers inject their own logger. `server/debug.ts` (`debugLog`/`debugWarn`) has been removed — use `createLogger(scope).debug/.warn`.

## Conventions worth knowing

- `Options.includePartialMessages` defaults to `true` on session create so clients can render streaming deltas. Callers can override.
- When a session is deleted while permissions are pending, each pending is resolved as `{ behavior: 'deny', message: 'session closed', interrupt: false }` so SDK awaiters don't hang.
- The deny path always returns `interrupt: false` — the model sees the deny result and re-plans instead of aborting the whole turn.
- `SessionManager.send()` and `sendContent()` broadcast the user message to local subscribers and history *in addition to* pushing it into the SDK input. The manual broadcast gives the UI an instant "I sent" bubble without waiting for the SDK to read the input queue. SDK 0.3 *does* echo top-level user input back through the Query stream (sometimes as `SDKUserMessageReplay` with `isReplay=true`, sometimes — first turn after spawn — as plain `SDKUserMessage` with no replay marker), so `session-pump.ts` filters those out. The discriminator is `parent_tool_use_id === null`: top-level user input has it null and is dropped (already broadcast), while tool results and sub-agent outputs have it set and are forwarded normally.
- `HttpError(status, message)` thrown from the manager is translated to a JSON response by the `onError` hook in `buildApiRouter`.
- Server-side defaults (model list, recap model, etc.) are loaded from `~/.claude-react-web/config.json`, not env vars — `server/config.ts` reads no `process.env`. The CLI `--model` flag and the in-app settings panel are the override paths. See `CONFIG.md` for the full field reference.
- Context-window size presets (`contextSteps`) have been removed. The context window is now determined by the SDK/model automatically.
- Publishing: no `publishConfig` in package.json — pass `--registry` on `npm publish` if you want a non-default target.
- QuestionDialog: after the user answers, the dialog lingers for ~3s showing the answer inline (via `initialAnswers` prop), then auto-dismisses. Questions also support an "Other" free-text option.
- `Shift+Tab` cycles through permission modes (default → auto-accept → bypass).
- `api_retry` system messages render as an amber retry pill in the WorkingBubble (wait time + attempt count, e.g. "26s 7/10", to the right of the timer / token-rate chips; the phase label KEEPS its slot, dimmed via `.working-bar-retry`; `waiting` suppresses the pill), never as a transcript row — the transient `mirror.apiRetry` slot is the single source (`toTranscriptItem` returns null for it; the ring copy exists so a reconnecting tab's incremental replay re-arms the slot). Every `system/api_retry` on the host stream is a MAIN-thread retry — verified against the CLI binary: the emitter attaches no `parent_tool_use_id`, and the subagent-stream forwarding loop skips the child's api_retry frames (a subagent's retry rides a `tool_progress` frame with data.type `agent_api_retry`, which the pump drops with every other tool_progress) — so the reducer's slot routing needs no parent check.
- Git: never spawn through a shell — always go through `runGit()` in `server/git.ts`. See the **Git integration** section for the full path-validation and `confirm: true` rules.
- There are THREE sidechain parents, not two: `Agent`/`Task`/`Explore` (→ SubagentCard), `Workflow` (→ WorkflowCard), and a **forked** `Skill`. Most Skill calls only load SKILL.md into the current conversation, but the CLI can also run one as its own agent and return just a report (`Skill "x" completed (forked execution)`); the fork's whole inner conversation then arrives as frames whose `parent_tool_use_id` is the Skill's tool_use id. WS-replay-verified against a live `code-review` call: 64 frames — 13 Bash, 10 Read, 9 nested `Agent` launches — hung off one id. This matters because `buildTranscriptRows` renders root frames only and each sidechain parent must own its children's rendering: before `activeSkills` (`getSkillStarts` → `SkillRecord.childCalls`, reducer branches next to the Workflow ones) that work was dropped with no owner and no entry point, while the nested Agents still got `activeSubagents` records — so their bar entry (per-agent chips at the time; the swarm pill since) appeared with no card behind it, and vanished for good when the records cleared. The Skill card's `forked execution` row is gated on `childCalls.length > 0` so the ordinary context-only call is untouched, and drill-in reuses SubagentOverlay (`parentToolUseIdFilter` = the Skill id, record adapted by `skillRecordAsSubagent`) rather than adding a third overlay.
- CSS: never hardcode color hex values — always use theme CSS variables (e.g. `var(--btn-hover-bg)` not `#242a35`). Every new color must be defined in both `:root` (dark) and `[data-theme="light"]` blocks. This prevents light/dark theme regressions.
- **Understand the problem before you touch anything.** Every change (CSS, logic, API, architecture) must start from a full understanding of the problem. Don't fix something the moment it "looks wrong" — first trace the context, understand the design intent, and locate the root cause, then act. Changing code before you understand it only treats the symptom and risks introducing new problems.
- **Prove root causes with logs before fixing — never guess, never add fallback code.** When debugging a bug, add temporary logging first (server `log.info` / client `console.log`), have the user reproduce it, and read the actual runtime values before claiming a root cause. Do NOT add "fallback / default / workaround" code as a speculative fix before the root cause is proven by data — guessing introduces unrelated changes, wastes round-trips, and masks the real problem. Remove the debug logs once the root cause is confirmed and the fix lands.
- **Don't add defensive code prematurely.** Handle only the states and inputs that can actually occur; write code so real errors surface loudly (throw, reject) instead of silently absorbing them with speculative null-checks, optional-chaining guards, try/catch, or fallbacks for failures never observed. Add a guard only when the failure is proven real (logs / repro) or an API contract demands it — a silent fallback masks bugs and makes the next debugging round harder.
- **Never commit unreviewed code.** Every code change must pass a review (self-review or peer review) before committing. Run the review against the full diff (`git diff HEAD` for uncommitted, or the commit range for a feature branch), verify findings, and fix any confirmed issues before the commit lands on `main`. A commit without a prior review is a process violation, not a shortcut.
- **Auto-trigger `code-review` for unreviewed changes.** Whenever there are uncommitted changes that have not yet been through a code review, run the `code-review` skill on the full diff before declaring the work done or committing — don't wait to be asked. Verify each finding against the code before fixing, and re-run the review on non-trivial fixes since those fixes are themselves unreviewed.

## App Plugins (Mods)

A separate extension system (`shared/app-plugins/`, `server/app-plugins/`, `src/app-plugins/`) lets plugins add menus, commands, settings, and panels to the **app shell** — distinct from the Claude Plugin Marketplace (`mp-store`, which extends the agent) and MCP. Plugins declare a `crw-plugin.json` manifest (commands/contextMenus/actions/configuration); background code runs in a per-plugin Node subprocess over JSON-RPC/stdio; the UI surface is declarative, never raw React/DOM. Trust model: a background plugin is a **trusted local program** (can `import node:fs`); permissions are consent UX + Host API feature flags, NOT a sandbox. The enforced boundaries are the network broker (SSRF: HTTPS-only, host allowlist, pinned-IP lookup), workspace adapter (realpath + `isPathInside`), and a cleaned subprocess env (no authToken).

Install paths: local-directory (`POST /api/app-plugins/install` `{source:{type:'local',path}}`) and **marketplace** (`POST /api/app-plugins/marketplaces` clones a GitHub repo → `app-plugins-marketplace.json` catalog or auto-scan → `POST /marketplaces/:id/plugins/:name/install`). `AppPluginRecord.source` is `local | marketplace` (marketplace provenance for updates/GC). Marketplace refresh `gitPull`s + revalidates installed plugins (permission escalation → `permission-required`).

**Update surface — deliberately shared with the Claude Plugin Marketplace.** Both settings panels expose the same row control (`MarketplaceUpdateButton`) and the same status-line wording, so one word — `Update` — means one thing in both: *sync this marketplace from upstream*. What that sync clears differs per subsystem and is inherent: the Claude panel's plugins are read live out of the clone, so the pull IS the update, while an App Plugin is an installed copy, so the App row pull refreshes the catalog and the per-plugin `Install`/`Update`/`Installed` buttons apply it (selective update needs that two-step, which is why the row button is pull-only). `POST /api/app-plugins/marketplaces/check-updates` is the App-side twin of the Claude panel's `check-updates` (non-mutating `git ls-remote` vs `lastSha`, per-marketplace errors isolated, `local` records excluded) and drives the row's warn state. The App panel's `Update all` stays available when nothing is badged — unlike Claude's — because its job also includes reconciling installed copies that lag the catalog with the repo already at HEAD. The `local` (bundled) marketplace has no upstream, so it renders no Update control at all; `seedBuiltinMarketplace` **re-parses** the bundled dir on every boot instead, since an app upgrade adds plugins to that directory while the persisted manifest still describes the previous release.

**`plugins/` directory** is the source of truth for official first-party plugins + the marketplace catalog (`app-plugins-marketplace.json`). It is published as a **separate lightweight GitHub repo** for distribution (users add its URL in the UI); `"files": ["dist"]` keeps it out of the host npm package. To publish/sync: `git subtree split --prefix=plugins -b marketplace-main && git push <marketplace-remote> marketplace-main:main`. The `translator` plugin (select text → right-click → LLM translate → popover) is the first. `fixtures/app-plugins/` holds framework-verification fixtures (not distributed). `plugins/` and `fixtures/` are eslint-ignored; `plugins/**/*.test.ts` runs under vitest.
